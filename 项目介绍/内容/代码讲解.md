1. ## 环境配置与初始化

**文件**: `src/real_finan/config.py`

从环境变量加载全部配置,是整个系统的配置中心。`AppConfig` 是一个 frozen dataclass(创建后不可修改),确保配置在运行时不会被意外篡改。

```Python
@dataclass(frozen=True)class AppConfig:
    output_dir: Path
    database_url: str
    redis_url: str | None# ... 15 个配置字段    @classmethoddef from_env(cls) -> "AppConfig":
        # 从 os.getenv() 读取所有配置,带默认值return cls(
            output_dir=Path(os.getenv("MAS_OUTPUT_DIR", "outputs")),
            database_url=os.getenv("MAS_DATABASE_URL", f"sqlite:///..."),
            # ...
        )
```

**设计要点**: `frozen=True` 看似不起眼,但在多 Agent 系统中这个约束确保了"配置不会被某个 Agent 意外修改后影响下游 Agent"——这是一个防御性设计。

**面试考点**: 为什么用 `@dataclass(frozen=True)` 而不是普通的 dict？→ 类型安全 + 不可变性保证 + IDE 自动补全。如果有 Agent 尝试修改 config,Python 运行时会抛 `FrozenInstanceError`,而不是静默地传递错误配置。

**文件**: `src/real_finan/llm.py`

三层 LLM 架构: Base(接口) → DeepSeekClient + LocalFallback(实现) → ResilientClient(容错代理)。

```Python

    def __init__(self, primary, fallback):
        self.primary = primary
        self.fallback = fallback or LocalFallbackLLMClient()
    def chat(self, ...):
        try:
            return self.primary.chat(...)
        except Exception:
            return self.fallback.chat(...)
```

**设计要点**: `ResilientLLMClient` 的 `except Exception` 是故意为之——上层的 7 个 Agent 不需要区分"网络超时"还是"API 返回格式错误",对它们来说都是"LLM 不可用,需要兜底"。代价是会吞掉代码 bug,但在这个项目规模下可控。

**面试考点**: `build_llm_client()` 在 `settings.api_key` 为 None 时 `primary=None`——这意味着一开始就走 fallback 路径。为什么不让 primary 永远不为 None？→ 因为如果在构造阶段就明确知道没有 API Key,不如直接走 fallback,避免后续每次调用都经历 `try-except` 的异常开销。

class SafeExpressionEvaluator(ast.NodeVisitor):
    allowed_nodes = (ast.Expression, ast.BinOp, ast.Add, ast.Sub,
                     ast.Mult, ast.Div, ast.Pow, ast.Load,
                     ast.Name, ast.Constant, ast.UnaryOp, ast.USub)

    def visit(self, node):
        if not isinstance(node, self.allowed_nodes):
            raise ValueError(f"Unsafe node: {type(node).__name__}")
        return super().visit(node)

    def visit_BinOp(self, node):
        left, right = self.visit(node.left), self.visit(node.right)
        if isinstance(node.op, ast.Add): return left + right
        if isinstance(node.op, ast.Mult): return left * right

1. ## Agent 运行时

**文件**: `src/real_finan/agents.py`

753 行,7 个 Agent 方法。每个 Agent 遵循相同的模式:

```Python
def supervisor(self, state):
    # 1. 从 state 中提取所需字段
    companies = extract_companies_from_query(state["query"], ...)

    # 2. 执行核心逻辑
    llm_brief = self.llm_client.chat(system_prompt=..., user_prompt=...)
    task_brief = parse_with_fallback(llm_brief).get("task_brief", ...)

    # 3. 构造返回字典
    update = {"companies": companies, "plan": plan, "task_brief": task_brief, ...}

    # 4. 记录审计 + 保存快照
    update.update(self._record("supervisor", "ok", detail))
    self.session_memory.save({**state, **update})

    # 5. 返回部分更新return update
```

**设计要点**: 每个 Agent 只 return 它修改的字段——LangGraph 自动将这些字段 merge 到总 state 中。Agent 不需要知道"完整 state 里还有什么其他字段"。

**面试考点**: 为什么 Agent 方法签名是 `(FinanceState) -> FinanceState` 但实际上 return 的是一个普通的 dict？→ `FinanceState` 是 `TypedDict`,Python 的 TypedDict 子类型赋值时不做校验。返回普通 dict 即可,LangGraph 框架会按 key merge。

1. ## 异步 Worker

**文件**: `src/real_finan/worker.py`

```Python
def work_forever():
    config = AppConfig.from_env()
    queue = RedisQueueManager(config.redis_url, config.redis_queue_name)
    while True:
        payload = queue.dequeue(timeout_seconds=5)  # BLPOP 阻塞等待if not payload:
            continue
        execute_analysis_job(job_id=payload["job_id"], query=payload["query"], ...)
```

**设计要点**: `dequeue(timeout_seconds=5)` 用 Redis BLPOP 的阻塞模式——不消耗 CPU 轮询。`timeout_seconds=5` 不是分析超时,而是"等待新任务"的超时——5 秒后如果没有新任务,`dequeue()` 返回 None,循环继续。

**面试考点**: 如果 Worker 在执行 `execute_analysis_job()` 时崩溃,任务会丢失吗？→ 会。BLPOP 已经将消息从队列中移除,没有 ACK 机制。改进方案: BRPOPLPUSH 做可靠队列,或改用 Celery。
