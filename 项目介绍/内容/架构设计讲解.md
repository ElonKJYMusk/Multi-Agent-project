**数据流简述**：

1. **客户端 → Service**: 用户 query + 可选 PDF 文件进入 `FinanceAnalysisService.analyze()`，PDF 经 PyMuPDF 解析为 `document_contexts`
2. **Service → System**: `FinanceMultiAgentSystem.run(query, thread_id, document_contexts)` 启动 LangGraph 流水线
3. **System → Agents**: StateGraph 按定义的路由依次调用 7 个 Agent，每个修改 `FinanceState` 的部分字段
4. **Agents → External**: Retrieval 调 MarketDataClient（实时行情）+ LLM（企业画像），写入 KnowledgeStore
5. **Synthesizer → Output**: 组装 11 章 Markdown 报告 + 图表 JSON，`export_run_artifacts()` 持久化到 `outputs/`

## 二、为什么选 LangGraph + FastAPI 架构？

**为什么不是 LangChain Chain？** Chain 只能表达 A→B→C 的线性流程。本项目需要条件路由（"缺数据时回去重新检索"）和循环（"重试 2 次后降级"），Chain 的表达力不够。StateGraph 的 ConditionalEdges 天然支持 DAG+回边。

**为什么不是 AutoGPT/CrewAI？** 这些框架的核心思想是"让 LLM 决定下一步做什么"。在金融分析场景中，这个理念有根本性矛盾——分析流程需要可审计，每个决策需要明确的理由。让 LLM 做路由判断，多了不确定性且无法保证每次都走相同的分析路径。

**为什么不是 Django/Flask？** FastAPI 的 async 支持、自动 OpenAPI 文档生成、Pydantic 集成更适合 API-first 的 AI 服务。Django 的 ORM 和模板系统对这个项目是冗余的。

**为什么 LLM 和业务逻辑不耦合？** `BaseLLMClient` 抽象（`llm.py:31-35`）只定义 `chat()` 方法签名。`ResilientLLMClient` 做容错代理。Agent 层不依赖具体的 LLM 实现——`build_llm_client()` 根据环境变量决定返回什么。替换 LLM 供应商只需实现一个新的 `BaseLLMClient` 子类。

## 三、核心模块设计

### 3.1 FinanceMultiAgentSystem（`graph.py:38-131`）

**设计理由**：这是系统的"装配器"——负责创建所有组件并编译图。放在一个类里而非分散在各处的理由是：① 所有依赖在 `init` 中显式注入，方便测试（可以传 mock LLM）；② `_build_graph()` 是图的唯一定义点，修改 Agent 编排只需要改这一处；③ `run()` 方法封装了 initial_state 构造和 `graph.invoke()` 调用，对上层暴露最简单的接口。

**关键方法**：

- `init`: 按顺序创建 SessionMemory → KnowledgeStore → ReasoningMemory → LLMClient → MarketDataClient → AgentRuntime → Checkpointer → Graph
- `_build_knowledge_store()`: 三级创建策略——Neo4j（有配置）→ NetworkX（Neo4j 连接失败）→ NetworkX（无配置）
- `_build_graph()`: 7 节点 + 4 条件边 + 2 固定边 + START/END
- `run()`: 构造 `initial_state`（12 个初始字段），调用 `graph.invoke()`

### 3.2 AgentRuntime（`agents.py:26-752`）

**设计理由**：`AgentRuntime` 包含 7 个 Agent 方法和 3 个基础设施引用。所有 Agent 方法签名统一为 `(FinanceState) -> FinanceState`——这不是 LangGraph 强制要求的（只要返回字典即可），但统一签名让代码更容易理解和测试。

**每个 Agent 的共同模式**：

1. 从 state 中提取所需字段
2. 执行核心逻辑（调 LLM、计算、数据融合）
3. 调用 `self._record()` 记录审计事件
4. 调用 `self.session_memory.save()` 保存状态快照
5. 返回 `FinanceState` 部分更新字典

### 3.3 状态管理的分层设计

```Plain
FinanceState (state.py) — 30+ 字段，所有 Agent 共享
    ├── 基础设施字段: query, companies, plan, audit_log
    ├── 数据层字段: retrieved_docs, market_snapshots, document_contexts
    ├── 计算层字段: financial_metrics, sentiment_analysis, risk_scores
    ├── 控制流字段: replan_reason, retries, degraded_mode, appendix_search_done
    └── 输出层字段: report_sections, executive_summary, final_report, chart_data
```

字段的分层对应 Agent 的执行顺序——数据层在 Retrieval 后填充，计算层在 Quant+Psychologist 后填充，输出层在 Synthesizer 后填充。控制流字段跨层使用，是路由判断的依据。

## 四、核心循环设计

### 4.1 正常路径

```Plain
START → Supervisor → Retrieval → Quant → Psychologist → Critic → Synthesizer → END
```

每个 Agent 执行约 1-5 秒（取决于 LLM API 延迟），完整路径约 15-25 秒。

### 4.2 重规划路径

```Plain
... → Retrieval → [数据缺口] → Replanner(retries=1) → Retrieval(补充检索)
                 → [数据仍不足] → Replanner(retries=2, degraded_mode)
                 → Synthesizer(降级模式)
```

Replanner 不是"修复问题"的 Agent——它只修改控制流字段（`retries`/`degraded_mode`/`appendix_search_done`），实际的问题修复在下一轮 Retrieval（带 `appendix_search_done=True` 参数）或 Synthesizer（带 `knowledge_hint` 提示）。

### 4.3 降级路径

降级模式下 Synthesizer 的行为变化：

- 给 LLM 的 prompt 中追加 `knowledge_hint`（`agents.py:419-422`）
- 财务指标章节显示 `[Degraded Analysis]` 标记
- SWOT 和情景推演仍然生成（基于规则推断 + LLM 知识）

## 五、LLM 容错架构设计

```Plain
build_llm_client()
    │
    ▼
ResilientLLMClient
    ├── primary: DeepSeekChatClient (有 API Key 时)
    │       └── httpx → DeepSeek API /chat/completions
    │       └── except Exception → 切 fallback
    │
    └── fallback: LocalFallbackLLMClient (始终存在)
            └── 基于 prompt 关键词的语义匹配
            └── 6 种 prompt 类型各有预设响应
```

关键设计决策：

1. **`except Exception`** **而不是更具体的异常**: 上层的 Agent 不关心 LLM 为什么失败——网络超时、鉴权错误、JSON 解析失败的结果一样是"LLM 不可用"
2. **Fallback 不返回空字符串**: 这是最重要的设计原则——空字符串导致下游 Agent 输出"数据不足"的废话报告。预设文本让报告即使在降级模式下也逻辑自洽
3. **`backend_name`** **追踪**: Agent 和报告都记录 `llm_backend` 字段，用户知道这份分析用的是 DeepSeek 还是 local-fallback

## 六、完整数据流图

```Plain
用户 Query "比较 Apple 和 Microsoft 的供应链风险"
    │
    ▼
[1. 公司识别] extract_companies_from_query()
    ├── 样本数据匹配: "Apple" in SAMPLE_FINANCIAL_DATA → ✓
    ├── 已知别名: "Apple" not in KNOWN_ALIASES → skip
    ├── PDF 检测: document_contexts 中有无 "Apple" → check
    └── LLM 提取: 前几步都没有才调 → not needed
    → ["Apple", "Microsoft"]

[2. 数据获取] retrieval()
    for Apple:
        ├── retrieve_company_payload("Apple") → SAMPLE_FINANCIAL_DATA["Apple"]
        │   ├── market_data: {revenue: 412.0, ebitda: 141.2, r_and_d: 33.4, ...}
        │   ├── supply_chain: {risk_level: "medium", signals: [...]}
        │   └── earnings_call_quotes: ["optimistic...", "supply constraints..."]
        ├── fetch_company_snapshot("Apple", "AAPL") → yfinance
        │   ├── current_price: 198.32
        │   ├── market_cap: 3.12e12
        │   └── trailing_pe: 32.5
        └── LLM Profile → "Apple Inc. 是全球最大的科技公司之一..."

[3. 定量计算] quantitative_analyst()
    base_data = {revenue: 412.0, ebitda: 141.2, r_and_d: 33.4, operating_income: 123.6}
    safe_execute_formula("ebitda / revenue", base_data) → 0.3427
    safe_execute_formula("r_and_d / revenue", base_data) → 0.0811
    calculate_derived_ratios() → {ebitda_margin: 0.3427, r_and_d_intensity: 0.0811, ...}

[4. 情绪分析] psychologist()
    earnings_call_quotes → analyze_sentiment() → {label: "bullish", positive_hits: 5, ...}
    earnings_call_quotes → LLM deep analysis → {confidence_score: 8, key_themes: [...], ...}

[5. 风险评分] critic()
    ebitda_margin=0.3427 → financial_risk = 9.0 - 0.3427*15 = 3.86
    supply_chain="medium" → operational_risk = 5.5 + sentiment_risk_flags*0.6
    sentiment skewed bullish → market_risk = 5.0 (cautious hits < positive hits)

[6. 报告合成] synthesizer()
    ┌─ Executive Summary (LLM 生成)
    ├─ Analytical Framework (模板)
    ├─ Company Profiles (LLM 生成)
    ├─ Financial Performance (指标表 + 推理链)
    ├─ Industry Context (规则 + LLM)
    ├─ SWOT Analysis (规则生成)
    ├─ Scenario Analysis (公式计算)
    ├─ Investment Thesis (规则 + LLM)
    ├─ Peer Comparison (LLM 生成)
    ├─ Compliance Review (LLM + 规则)
    └─ Methodology & Disclaimer (模板)

[7. 输出] export_run_artifacts()
    → outputs/{thread_id}_{timestamp}_report.md
    → outputs/{thread_id}_{timestamp}_audit.json
    → outputs/{thread_id}_{timestamp}_state.json
```

## 七、可扩展性设计

### 如何添加新的行情数据源

1. 在 `market_data.py` 中新增一个 `_fetch_from_xxx()` 方法
2. 在 `fetch_company_snapshot()` 的 `provider` 分支中添加新选项
3. 在 `AppConfig` 中添加 `xxx_api_key` 配置字段
4. 返回字典格式需与现有 `_fetch_from_yahoo()` 保持一致（字段名不变）

### 如何添加新的 LLM 后端

1. 实现 `BaseLLMClient` 子类，只需实现 `chat()` 方法
2. 在 `build_llm_client()` 中添加创建逻辑
3. 设置 `backend_name` 类属性用于追踪

### 如何添加新的公司数据

1. 在 `SAMPLE_FINANCIAL_DATA` 字典中添加新公司条目，遵循现有 schema
2. 在 `COMPANY_HINTS` 中添加公司名别名（PDF 识别用）
3. 在 `DEFAULT_TICKER_MAP` 中添加股票代码映射

### 如何添加新的财务指标

1. 在 `calculate_derived_ratios()` 中添加计算公式
2. 在 `build_chart_data()` 的 `metric_keys` 列表中添加新指标（会在前端展示）
3. 在 Synthesizer 的报告模板中添加展示行

### 如何添加新的报告章节

1. 在 Synthesizer 的 `S()` 调用序列中插入新章节
2. 如果需要 LLM 生成内容，添加新的 `self.llm_client.chat()` 调用
3. 如果需要图表数据，在 `build_chart_data()` 中添加对应的数据结构
