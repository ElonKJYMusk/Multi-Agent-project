# Real-Finan 企业级多智能体金融分析系统 项目简历

## 项目简介

我独立设计并实现了一个基于 LangGraph 的 7-Agent 金融分析系统，将投研分析拆解为 Supervisor→Retrieval→Quant→Psychologist→Critic→Replanner→Synthesizer 七个专业化协作节点。系统对外提供 FastAPI REST 接口，支持 PDF 财报上传、异步任务队列、多源行情数据融合。

## 核心功能

- **7-Agent 有状态流水线**：基于 LangGraph StateGraph 构建，7 个 Agent 通过条件边路由（`graph.py:83-104`），支持数据缺口检测→自动重规划→超限降级的三级容错机制。Agent 间通过 `FinanceState` TypedDict（30+ 字段）传递状态，InMemorySaver 做对话级持久化。
- **AST 安全公式求值器**：用 `ast.NodeVisitor` 白名单模式实现（`tools.py:13-69`），只放行 7 种安全 AST 节点，物理隔绝代码注入。支持 `ebitda / revenue` 等级联公式计算，替代 `eval()` 的同等效果但零风险。
- **多源数据融合管线**：内置样本数据库（Apple/Microsoft 2025 财报）+ yfinance 实时行情（Yahoo v7/v8 API）+ PDF PyMuPDF 文本抽取三层数据源在 Retrieval Agent 内合并，LLM 同步生成 150 字企业画像。
- **LLM 双链路容错**：`ResilientLLMClient`（`llm.py:89-104`）封装 primary→fallback 切换逻辑，DeepSeek API 超时/鉴权失败时自动降级到 `LocalFallbackLLMClient`——不是返回空字符串，而是根据 prompt 中的关键词（`task_brief`/`executive summary`/`合规`）匹配预设的中文分析文本，保证报告可读性。
- **五维风险评分模型**：Critic Agent 中实现了因子驱动的风险计算——EBITDA Margin 映射财务风险（`9.0 - margin×15`，夹持1.5-9.5），供应链等级映射运营风险，情绪偏态映射市场风险（`tools.py:331-396`），全部在代码中硬校准。
- **机构级 11 章报告**：Synthesizer 组装 SWOT、Base/Bull/Bear 情景推演、投资论点、同行对标、合规审计（`agents.py:455-728`），同时生成结构化图表数据供前端可视化。

**项目背景：** 传统金融分析依赖人工从多源数据（财报PDF、行情接口、新闻舆情）中提取信息并撰写报告，一个分析师覆盖单家公司的完整分析通常需要 4-6 小时。现有 AI 分析工具多为单次 LLM 调用，缺乏结构化推理链和多维度交叉验证，容易出现"看起来合理但数据对不上"的幻觉输出。我需要构建一个能模拟真实投研团队分工协作的多 Agent 系统——不同 Agent 负责不同分析维度，各自产出可追溯的结果，最终由专职 Agent 整合成有数据支撑的报告。

**主要负责：**

**一、多 Agent 流水线架构设计与实现：** 这是整个项目的骨架。我在 LangGraph StateGraph 上定义了 7 个 Agent 节点和 4 条条件路由边（`graph.py:71-106`），每个节点对应一个独立的分析职能。关键设计决策包括：① 所有 Agent 共享 `FinanceState` TypedDict（`state.py:12-43`）而非各自维护私有状态——这样做的好处是调试时只需看一份 JSON 就能还原完整推理链；② 条件路由不走 LLM 判断，而是检查 state 中的显式信号（`replan_reason` 是否为 None、`degraded_mode` 是否为 True）——避免路由本身引入额外延迟和不确定性；③ 三级容错路径（数据缺口→补充检索→降级合成）对应 retries 计数器，2 次为阈值（`agents.py:393-394`），这个数字是我在本地反复跑 Apple+Microsoft 双公司对比场景后定的——1 次不够处理附录缺失，3 次以上用户等待时间过长。

**二、AST 安全表达式引擎：** Quant Agent 需要对公式求值（如 `ebitda_margin = ebitda / revenue`），但 `eval()` 不安全，正则解析又处理不了嵌套表达式。我在 `tools.py:13-75` 用 `ast.NodeVisitor` 实现了一个白名单求值器——只放行 `Expression/BinOp/Add/Sub/Mult/Div/Pow/Name/Constant/UnaryOp/USub` 这 11 种节点类型，其余任何 AST 节点直接抛 `ValueError`。这个实现约 60 行，但覆盖了所有财务指标计算需求。配合 `safe_execute_formula()` 包装函数，上层调用方式与 `eval()` 一样简洁，但代码审查时不需要做任何安全审计。

**三、LLM 容错与降级架构：** 系统既要支持 DeepSeek API 全能力模式，又要确保本地 demo 无密钥可跑。我设计了 `ResilientLLMClient`（`llm.py:89-104`）作为代理层——构造函数接收 primary 和 fallback 两个 client，`chat()` 方法先尝试 primary，捕获任何 Exception 后自动切 fallback。关键是 fallback 不返回空字符串：`LocalFallbackLLMClient`（`llm.py:66-86`）根据 prompt 中的关键词（`task_brief`/`executive summary`/`合规`）返回预设分析文本，这些文本不是硬编的占位符，而是我根据 Apple+Microsoft 真实对比场景写的金融分析段落，确保无 API 条件下报告仍然逻辑自洽。

## 面试话术参考

**项目介绍 (30秒版本)**

我做的是一个叫 Real-Finan 的金融分析多智能体系统，独立开发。它用 LangGraph 编排了 7 个专业 Agent 协同完成投研分析——从公司识别、多源数据融合、五维财务指标计算、管理层情绪分析、到风险评分和合规审计，最后输出一份含 SWOT 和三种情景推演的 11 章机构级报告。LLM 层做了 DeepSeek + 本地关键词回退的双链路容错，没 API 密钥也能跑通完整流水线。对外是 FastAPI REST 接口，支持 PDF 财报上传解析和 Redis 异步任务队列。

**技术深度展示 (多Agent流水线架构)**

LangGraph StateGraph 是这项目的核心。我定义了 7 个节点，每个节点函数签名为 `(FinanceState) -> FinanceState`，通过 `FinanceState` TypedDict 在节点间传递全部上下文——`state.py` 里这个 TypedDict 有 30 多个字段，覆盖从用户 query 到最终 report 的完整链路。

路由不走 LLM，而是用纯 Python 的条件函数检查 state 中的信号位。比如 Retrieval 节点执行完后，`route_after_retrieval()` 检查 `state.get("replan_reason")`——如果有值说明数据缺口需要重规划，返回 `"replanner"`；否则返回 `"quant"` 进入定量分析。这个设计让路由延迟为零（不走网络），而且可测试。

最复杂的路由是 Replanner。`retries` 计数器从 0 开始，第一次进 Replanner 时 `retries` 变 1，设置 `appendix_search_done=True`，路由回 Retrieval 做补充检索。第二次进 Replanner 时 `retries` 变成 2，触发 `degraded_mode=True`，跳过所有中间节点直接进 Synthesizer，Synthesizer 里的 `knowledge_hint`（`agents.py:419-422`）会告诉 LLM "数据有限，请用你的公开知识补充分析"——而不是输出一句 "数据不足无法分析"。这个 2 次阈值是跑了几十次 Apple+Microsoft 场景后定的。

**遇到的最大挑战**

最大的问题是 DeepSeek API 返回的 JSON 经常被 Markdown 代码块包裹（````json ... ````），直接 `json.loads()` 必抛异常。一开始我加了个简单的 `strip('`')`，但遇到 `` ```json\n{...}\n``` `` 这种格式就挂了。后来在 `tools.py:425-430`写了`parse_with_fallback()`，用字符串 split 逐层剥——先检测是否以 `` ``` `` 开头，是就去掉第一行和最后一行，再 `json.loads()`。Supervisor 和 Psychologist 两个 Agent 的 LLM 调用都依赖这个函数，是调用链上的单点。如果再重构，我会在 DeepSeekChatClient 层统一做 response post-processing，而不是在每个 Agent 里各自调用 `parse_with_fallback`。

另一个棘手的问题是无 API 密钥时的 fallback 文本质量。一开始 LocalFallbackLLMClient 所有分支都返回 "已完成分析" 这种废话，导致 Synthesizer 生成的报告全是占位符。后来我针对 6 个不同的 prompt 关键词（`task_brief`/`executive summary`/`合规` 等）写了对应的预设分析文本——这些文本基于 Apple 和 Microsoft 的真实对比数据，确保本地 demo 的报告读起来也像那么回事。

## 面试常见追问

**Q: 为什么用 LangGraph 而不是自己写一个简单的 for 循环调用多个 Agent？**

A: 一开始确实可以写 `for agent in agents: state = agent(state)`，但当需要条件分支（"数据不够就回去重新检索"）和循环（重试 2 次后降级）时，手写状态机很快会变成一堆 if-else 嵌套。LangGraph 的 StateGraph + ConditionalEdges 天然表达 DAG+回边，7 个节点 4 条条件路由的图在 `graph.py:71-106` 只用了 36 行代码说清楚。更重要的一点是 LangGraph 的 checkpointer（InMemorySaver）自动保存每个节点执行后的状态快照，调试时我可以回溯到任意节点看当时的 state 是什么——这在手写循环里需要自己实现序列化逻辑。

**Q: LocalFallbackLLMClient 返回的是预设文本，这算不算"假分析"？**

A: 这取决于怎么看。从技术角度，LocalFallbackLLMClient 不是设计来替代 DeepSeek 的——它的定位是"开发/演示模式下的兜底方案"。正式部署场景一定配 API 密钥。但我不接受"无 API 就跑不起来"的用户体验——你 clone 下来 `pip install -r requirements.txt && python run_demo.py` 应该立刻看到一份像样的报告。预设文本的价值在于验证整个流水线的串联逻辑是否正确，而不是验证 LLM 输出质量。两者解决的是不同层次的问题。

**Q: Quant Agent 的 AST 求值器只支持加减乘除，如果以后需要更复杂的公式怎么办？**

A: `SafeExpressionEvaluator` 的白名单设计是刻意保守的——安全优先于功能。目前支持的运算符（`+ - * / **`）已经覆盖所有财务指标计算需求。如果未来需要 `sqrt()`、`log()` 等数学函数，我会在 `visit_Call` 中单独维护一个安全函数白名单，只放行 `math.sqrt`、`math.log` 等纯数学函数，仍然拒绝任意 callable。扩展方案在架构设计文档里有详细讨论。关键原则是：每增加一个白名单节点，必须有明确的业务需求驱动，不做"先开权限以后再用"的妥协。

**Q: 7 个 Agent 的设计是固定的吗？如果要分析的公司不需要情绪分析怎么办？**

A: 目前所有 7 个 Agent 都会执行，但每个 Agent 内部有自己的短路逻辑。Psychologist 在 `earnings_call_quotes` 为空时仍会跑——它会用 LLM 根据公开知识推断管理层语气，而不是直接跳过。如果确实要跳过，可以在 Supervisor 的 planning 阶段根据 query 动态调整节点列表，用 LangGraph 的 `add_node`/`add_edge` 在编译前做条件图构建。但这个需求在当前的金融分析场景里没出现过——情绪分析几乎是每次投研的必选项。

**Q: 系统的最大瓶颈在哪？**

A: 目前最明显的瓶颈在 LLM API 延迟——单次分析 4-6 次 API 调用，每次 1-5 秒，DeepSeek API 高峰期可能更长。如果跑 3 家以上公司的对比分析，Synthesizer 的 prompt 会很长（所有公司数据都在一个 user_prompt 里），max_tokens=500 可能不够。短期优化：对不同 Agent 的 API 调用做并行化（Retrieval 里的企业画像生成和 Quant 的同行对标可以同时调）。中期方案：对常见公司做分析结果缓存，避免重复调用。

1. ## LangGraph StateGraph 多智能体编排

**核心概念**：LangGraph 是 LangChain 生态中的有状态图执行框架。不同于 Chain 的线性调用（A→B→C），StateGraph 允许定义节点（Node）、普通边（Edge）和条件边（ConditionalEdge），形成有向图甚至带回边的循环图。每个节点接收一个共享状态字典，处理后返回部分更新——框架自动做状态合并。StateGraph 的关键能力是：① 条件路由——根据当前状态决定下一个节点；② 循环——允许回到已访问节点（如重试）；③ Checkpointer——每个节点执行后自动保存状态快照，支持断点续跑和时间旅行调试。

它的主要替代方案是 AutoGPT/CrewAI 这类让 LLM 自主决定下一步的方案。区别在于：StateGraph 的控制流是显式定义在代码中的（确定性），而 AutoGPT 的控制流由 LLM 输出决定（非确定性）。金融分析场景对可审计性要求极高——你需要确切知道"为什么这个分析走了重规划路径"——所以确定性控制流更适合。

**本项目**：`graph.py:71-106` 中 `_build_graph()` 方法定义了完整的 7 节点 StateGraph。节点通过 `workflow.add_node("supervisor", self.runtime.supervisor)` 注册，条件边通过 `workflow.add_conditional_edges("retrieval", route_after_retrieval, {...})` 注册。路由函数（如 `route_after_retrieval:21-22`）是纯 Python 函数，检查 `state.get("replan_reason")` 是否为 None 来决定方向——不涉及 LLM 调用。

```Python
# graph.py:71-106 — StateGraph 构建def _build_graph(self):
    workflow = StateGraph(FinanceState)
    workflow.add_node("supervisor", self.runtime.supervisor)
    workflow.add_node("retrieval", self.runtime.retrieval)
    workflow.add_node("quant", self.runtime.quantitative_analyst)
    workflow.add_node("psychologist", self.runtime.psychologist)
    workflow.add_node("critic", self.runtime.critic)
    workflow.add_node("replanner", self.runtime.replanner)
    workflow.add_node("synthesizer", self.runtime.synthesizer)

    workflow.add_edge(START, "supervisor")
    workflow.add_edge("supervisor", "retrieval")
    workflow.add_conditional_edges(  # ← 关键：条件路由不走LLM"retrieval", route_after_retrieval,
        {"quant": "quant", "replanner": "replanner"},
    )
    # ... 更多条件边 ...
    workflow.add_edge("synthesizer", END)
    return workflow.compile(checkpointer=self.checkpointer)
```

**面试追问**：StateGraph 对比手写状态机有什么不可替代的优势？→ Checkpointer 自动持久化。手写状态机每次节点执行后需要手动序列化 state，StateGraph 的 InMemorySaver 在 `compile()` 时注入，每个节点返回后自动存档——这让调试时可以回溯到任意节点的快照，对于 7 个节点的复杂流程这在开发阶段节省了大量时间。

1. ## 条件路由与容错状态机

**核心概念**：在多 Agent 系统中，不是所有请求都走相同的路径。条件路由（Conditional Routing）允许根据当前状态选择下一个节点，是构建容错系统的核心机制。设计条件路由时有两个关键决策：① 路由判断依据——用 LLM 判断（灵活但不确定）还是用代码规则判断（确定但需预定义）？② 循环终止条件——如何在重试次数和用户体验之间平衡？

在金融分析场景中，典型的路由触发条件包括：数据缺失（需要重新检索）、计算失败（需要降级处理）、合规发现（需要修订报告）。这些条件应该通过检查状态中的显式信号来判断，而非让 LLM 来判断"现在是否需要重试"——后者既增加延迟又引入不确定性。

**本项目**：系统定义了 4 个路由函数（`graph.py:21-35`）和 1 个 Replanner 节点（`agents.py:392-404`）共同实现三级容错：

1. **数据缺口检测**（`route_after_retrieval:21-22`）：Retrieval 执行后，如果任一公司的 `retrieved_docs` 缺少市场数据或附录数据，设置 `replan_reason`，路由到 Replanner
2. **计算不可行检测**（`route_after_quant:25-26`）：Quant 执行后，如果某公司 `financial_metrics` 为空（数据不足以计算），设置 `replan_reason`
3. **降级模式触发**（`agents.py:393-394`）：`retries >= 2` 时激活 `degraded_mode`，Replanner 不再路由回 Retrieval，而是直接进 Synthesizer
4. **降级模式路由**（`route_after_replanner:34-35`）：降级模式下跳过 Retrieval，直接合成报告

```Python
# graph.py:34-35 — 降级模式下的路由逻辑def route_after_replanner(state: FinanceState) -> str:
    return "synthesizer" if state.get("degraded_mode") else "retrieval"
```

**面试追问**：为什么 retries 阈值设为 2 而不是 3 或 1？→ 基于 Apple+Microsoft 双公司场景反复测试。1 次重试能覆盖大部分附录缺失场景（一次补充检索就够了），但少数情况下 YFinance API 波动会导致第二次也失败。3 次以上用户等待时间过长（每次 Retrieval 涉及多次 LLM 调用），综合考虑选 2 次为阈值——这是一个经验值而非理论最优值。

1. ## TypedDict 全链路状态管理

**核心概念**：在多 Agent 系统中，状态管理决定了 Agent 之间如何通信。三种常见模式：① 消息传递（Agent A 的输出作为 Agent B 的输入）——简单但丢失中间状态；② 全局状态对象（所有 Agent 读写同一个 state）——信息完整但需要类型约束；③ 事件总线（Agent 发布/订阅事件）——解耦但调试困难。

`TypedDict` 是 Python 3.8+ 的类型提示机制，允许定义字典的键名和值类型，但不强制运行时校验。在 LangGraph 中，`StateGraph(TypedDict)` 的泛型参数告诉框架状态字典的 schema，框架利用这个 schema 做增量合并——每个节点只需 return 它修改的字段，框架自动 merge 到完整 state。

**本项目**：`state.py:12-43` 定义了 `FinanceState(TypedDict, total=False)`——注意 `total=False` 意味着所有字段都是可选的，这是实际需要，因为不同节点逐步填充不同字段。Supervisor 填充 `companies`/`plan`/`task_brief`，Retrieval 填充 `retrieved_docs`/`market_snapshots`/`company_profiles`，Quant 填充 `financial_metrics`，以此类推。LangGraph 的增量合并保证每个节点只需关心自己的产出字段。

```Python
# state.py:12-43 — FinanceState 定义（部分字段）class FinanceState(TypedDict, total=False):
    query: str                          # 用户原始查询

    compliance_findings: list[str]      # Critic 合规发现

**面试追问**：`total=False` 意味着所有字段可选，类型检查器无法发现"某个节点忘记填充必要字段"的问题——如何保证运行时安全？→ 当前依赖 `state.get("field")` 的安全访问模式，每个节点对缺失字段有默认值处理。如果要加运行时校验，可以在每个节点入口处用 pydantic 做 state 子集的 validation。目前没有加是因为 7 个节点的开发节奏下类型约束的 ROI 不够高——bug 更多出现在 LLM 输出解析而非字段缺失。

1. ## AST 安全表达式求值

**核心概念**：`eval()` 可以执行任意 Python 代码，在生产环境中是安全红线。但财务分析确实需要运行时根据配置计算动态公式（如 `ebitda_margin = ebitda / revenue`）。Python 的 `ast` 模块提供了将字符串解析为抽象语法树（AST）的能力——语法树是一个树形结构，每个节点代表一个语法元素（如 `BinOp` 代表二元运算，`Name` 代表变量引用）。

`ast.NodeVisitor` 是访问者模式的实现：遍历 AST 树，对每种节点类型调用对应的 `visit_*` 方法。通过在 `visit()` 入口处做节点类型白名单校验，可以物理上拒绝任何非数学运算节点（如 `Call` 函数调用、`Attribute` 属性访问），从而实现安全的表达式求值。

**本项目**：`tools.py:13-69` 实现 `SafeExpressionEvaluator(ast.NodeVisitor)`。核心安全机制在 `visit()` 方法——它重写了基类的 `visit()`，在 dispatch 前检查节点类型是否在 `allowed_nodes` 白名单中。白名单只包含 7 大类节点：`Expression/BinOp/Add/Sub/Mult/Div/Pow/Name/Constant/UnaryOp/USub`。任何 `Call`（函数调用）、`Attribute`（属性访问）、`Subscript`（下标访问）等节点都会直接抛 `ValueError`。

```Python
# tools.py:13-34 — 白名单 + 入口校验class SafeExpressionEvaluator(ast.NodeVisitor):
    allowed_nodes = (
        ast.Expression, ast.BinOp, ast.Add, ast.Sub,
        ast.Mult, ast.Div, ast.Pow, ast.Load,
        ast.Name, ast.Constant, ast.UnaryOp, ast.USub,
    )

    def visit(self, node: ast.AST) -> float:
        if not isinstance(node, self.allowed_nodes):
            raise ValueError(f"Unsafe node detected: {type(node).__name__}")
        return super().visit(node)
```

配合 `safe_execute_formula()`（`tools.py:72-75`），上层调用只需传入公式字符串和变量字典，返回计算结果。这个约 60 行的实现覆盖了所有财务指标计算需求，同时通过了安全审查。

**面试追问**：如果业务需要 `sqrt()` 和 `log()`，如何扩展而不破坏安全性？→ 在 `visit_Call` 中维护数学函数白名单 `{"sqrt": math.sqrt, "log": math.log}`，只放行纯数学函数，拒绝任何有副作用的 callable。同时检查 `node.func` 必须是 `Name` 节点（拒绝 `module.func` 形式的属性调用）。每增加一个白名单条目需要有明确的业务需求文档。

1. ## LLM 容错模式（Primary-Fallback）

**核心概念**：LLM API 是不可靠的——可能因为网络抖动、API 限流、鉴权过期、服务降级等原因调用失败。容错模式的核心思想是：系统在 LLM 不可用时仍能提供可用的输出，而非直接报错。

三种常见的容错策略：① 重试（Retry）——同一 LLM 失败后等待重试；② 切换（Failover）——切换到备用 LLM；③ 降级（Fallback）——用规则引擎/缓存/预设文本替代 LLM 输出。本项目的 `ResilientLLMClient` 选择了策略②+③的组合：优先用 DeepSeek API，失败后不重试（避免增加用户等待时间），直接切换到内置规则引擎。

**本项目**：`llm.py:89-104` 的 `ResilientLLMClient` 是一个代理模式实现。构造函数接收 `primary` 和 `fallback` 两个 `BaseLLMClient` 实例。`chat()` 方法先尝试 `primary.chat()`，`except Exception` 捕获所有异常类型后切 `fallback.chat()`。注意异常捕获范围是 `Exception` 而非更具体的类型——这是故意为之：对于上层 Agent 来说，网络错误、鉴权错误、超时错误的结果都一样是"LLM 不可用"，不需要区分处理。

`LocalFallbackLLMClient`（`llm.py:66-86`）不是返回空字符串，而是根据 prompt 中的关键词匹配返回预设分析文本。目前覆盖了 6 种 prompt 类型：Supervisor 的 task_brief、Synthesizer 的 executive_summary、Critic 的合规审计、以及通用回退。

```Python
# llm.py:89-104 — ResilientLLMClient 核心逻辑class ResilientLLMClient(BaseLLMClient):
    def __init__(self, primary, fallback=None):
        self.primary = primary
        self.fallback = fallback or LocalFallbackLLMClient()

    def chat(self, system_prompt, user_prompt, temperature=0.2, max_tokens=600):
        if self.primary is None:
            return self.fallback.chat(...)
        try:
            return self.primary.chat(...)
        except Exception:
            self.backend_name = self.fallback.backend_name
            return self.fallback.chat(...)
```

**面试追问**：为什么不在 primary 失败时加重试逻辑？→ 因为重试增加延迟且成功率有限。DeepSeek API 的不稳定性通常不是单次抖动——如果第一次超时（45 秒），第二次大概率也超时。用户等待 90 秒后得到 fallback 结果 vs 立即得到 fallback 结果，后者体验更好。如果未来的场景对输出质量要求极高（如合规审查），可以在 ResilientLLMClient 上层加重试，而不是改这个基础组件。

1. ## 多源数据融合检索

**核心概念**：RAG（Retrieval-Augmented Generation）的核心思想是让 LLM 在生成之前先检索相关上下文。传统 RAG 聚焦于向量检索——文档切 chunk → embedding → 向量相似度搜索。但在金融分析场景中，"相关上下文"不止文本——还包括结构化市场数据（股价、PE、市值）、半结构化财报数据（Revenue/EBITDA 指标）、以及 LLM 自身的行业知识。

多源数据融合的关键挑战是：不同数据源的 schema 不一致、时效性不同、可信度不同。需要设计一个统一的数据融合层，将异构数据归一化为 Agent 下游可统一消费的格式。

**本项目**：Retrieval Agent（`agents.py:121-189`）实现了三层数据融合，针对每家公司构建统一的 `payload` 字典：

1. **样本数据库**（`tools.py:88-155` 的 `retrieve_company_payload()`）：从 `SAMPLE_FINANCIAL_DATA` 字典中匹配已知公司，提取 `market_data`、`supply_chain`、`earnings_call_quotes`
2. **实时行情**（`market_data.py:31-54`）：通过 `MarketDataClient.fetch_company_snapshot()` 调用 yfinance 或 Alpha Vantage API，获取实时股价、PE、市值、52周高低点
3. **PDF 文档**（`tools.py:225-239` 的 `summarize_document_context()`）：从上传的 PDF 中提取与该公司的相关指标和文本片段，与样本数据做合并（PDF 提取的 Revenue 覆盖样本数据中的默认值）

数据优先级：如果 PDF 提取到了指标（如 Revenue），则覆盖样本数据中的对应值——因为 PDF 通常是用户上传的真实财报，优先级最高。

```Python
# agents.py:128-144 — 三层数据融合核心逻辑for company in state["companies"]:
    document_summary = summarize_document_context(document_contexts, company)
    payload = retrieve_company_payload(company, ...)
    live_market = self.market_data_client.fetch_company_snapshot(...)

    payload["live_market"] = live_market
    # PDF 提取的指标覆盖样本数据if document_summary["metric_hints"]:
        payload["market_data"].update({
            "revenue_2025": document_summary["metric_hints"].get("revenue",
                payload["market_data"].get("revenue_2025")),
        })
```

**面试追问**：为什么不用向量数据库做语义检索？→ 对于这个项目的规模和场景，正则匹配 + 结构化数据融合足够了。当前处理的文档量是"用户上传 1-5 份财报 PDF"，不是"检索百万份研报"。向量数据库引入 embedding 模型选择、索引构建、相似度调参等额外复杂度，对于用户上传少量 PDF 做分析的场景是过度设计。如果扩展到全市场研报检索，才需要考虑向量化。

1. ## 深度情绪分析（规则引擎 + LLM 双引擎）

**核心概念**：金融文本的情绪分析不同于通用情感分析——"管理层表示对供应链恢复持谨慎乐观态度"在通用模型中可能是 neutral/positive，但对金融分析师来说这是 cautious 信号。金融情绪分析需要三个层次：① 表面情绪（正/负面词汇计数）；② 深层语气（LLM 理解修饰语和上下文）；③ 信心评分（管理层表述的确定性程度）。

双引擎设计（规则 + LLM）的优点：规则引擎提供可解释的基线（哪个词触发了哪种判断），LLM 提供语义理解深度（识别"despite strong headwinds"这类需要上下文才能正确解读的表述）。两者结合既有可审计性又有深度。

**本项目**：`tools.py:242-306` 实现了双层情绪分析：

第一层 `analyze_sentiment()`（`242-261`）：词袋模型。维护 `positive_markers`（16 个英文正向词）和 `caution_markers`（12 个警示词）两个词表，对引述文本做小写匹配计数。`positive_hits >= caution_hits → "bullish"`，否则 `"cautious"`。这个算法的局限很明显——"not optimistic" 会被错误计为正向——但作为基线它足够简单且可解释。

第二层 `analyze_sentiment_deep()`（`273-306`）：当 LLM 可用时，将最多 5 条引述（截断至 2000 字符）发给 LLM，要求返回 JSON 格式的深度分析：`overall_tone`（bullish/cautious/neutral）、`confidence_score`（0-10）、`key_themes`（主题列表）、`risk_flags`（风险标记）、`strategic_priority`（战略重点）。LLM 失败时回退到第一层的结果。

```Python
# tools.py:280-289 — LLM 深度情绪分析 prompt
response = llm_client.chat(
    system_prompt=(
        "你是管理层语气分析专家。请基于提供的财报引述进行深度分析，""返回 JSON 格式: {\"overall_tone\": \"bullish/cautious/neutral\", ""\"confidence_score\": 0-10, \"key_themes\": [\"主题1\",\"主题2\"], ""\"risk_flags\": [\"风险1\"], \"strategic_priority\": \"战略重点\"}"
    ),
    user_prompt=f"管理层引述:\n{joined_quotes}",
    temperature=0.1, max_tokens=250,
)
```

**面试追问**：规则引擎的正向词表会误判否定句式（"not optimistic" 被记为 positive），为什么不引入简单的否定词处理？→ 确实应该引入。最简单的 fix：在计数前先检测每个 marker 前 3 个 token 内是否有否定词（not/never/hardly/fail to），如果有则跳过该次匹配或反转计数。当前版本没加的原因是——这个规则引擎本身只是 LLM 分析前的基线，一旦 LLM 可用，分析结果就切到 LLM 版本了。但如果未来要做完全离线的情绪分析，否定词处理是第一个要加的。

1. ## 多因子风险评分模型

**核心概念**：金融风险不是单一维度的——一家公司可能财务健康（低财务风险）但供应链高度集中（高运营风险）。多因子风险模型将风险分解为多个独立维度，每个维度用可量化的输入因子驱动评分，最终形成风险雷达图。

风险评分的核心挑战在于因子校准——为什么 EBITDA Margin 25% 对应财务风险 5.25 而不是 5.0？这需要领域知识，也需要在代码中明确写出映射逻辑，让后续使用者可以检查和调整。

**本项目**：Critic Agent（`agents.py:315-387`）实现了五维风险评分：

1. **财务风险**：`9.0 - ebitda_margin × 15`，夹持在 1.5-9.5 之间。ebitda_margin=0.30 → 4.5（低风险），0.10 → 7.5（高风险）
2. **运营风险**：基线由供应链等级决定（low=2.5, medium=5.5, high=8.0），加上情绪分析中的风险标记数 × 0.6
3. **市场风险**：基线 5.0，情绪偏 cautious 加 1.8，52周价格位置 > 0.8（接近高点）加 1.2，< 0.2（接近低点）减 1.0
4. **监管风险**：固定 3.5（当前未做行业细分）
5. **供应链风险**：直接映射供应链等级（low=2.0, medium=5.0, high=8.0）

```Python

1. ## 知识图谱在企业分析中的应用

**核心概念**：知识图谱（Knowledge Graph）将实体和关系建模为图结构（节点=实体，边=关系），适合表达"某公司→有指标→EBITDA Margin→值为 34%"这类多跳关系。相比关系型数据库，图数据库的优势在于关系遍历——"找出所有供应链风险等级为 high 的公司及其共同的供应商"这类查询在图数据库中只需一次遍历，在关系型数据库中需要多次 JOIN。

在金融分析场景中，知识图谱的典型应用包括：公司-指标关系、公司-子公司关系、供应链上下游关系、行业分类层级。

**本项目**：`knowledge_store.py` 定义了两个 KnowledgeStore 实现：`InMemoryKnowledgeStore`（基于 NetworkX DiGraph）和 `Neo4jKnowledgeStore`（基于 Neo4j 图数据库）。两者遵循相同的 `KnowledgeStore` Protocol（`ingest_company_document + snapshot`），上层 AgentRuntime 不感知底层实现。

在 Retrieval Agent 中，每次分析会调用 `knowledge_memory.ingest_company_document()` 将融合后的公司数据写入图。每次写入产生 4 种节点类型——Company、Metric、Risk、Document——以及对应的 HAS_METRIC/HAS_RISK/HAS_DOCUMENT 关系。单次分析约产生 12-20 个节点和 18-30 条边。

```Python
# knowledge_store.py:20-41 — NetworkX 版本的数据摄入def ingest_company_document(self, company, payload):

    for metric_name, value in payload.get("market_data", {}).items():
        metric_id = f"{company}:{metric_name}"
        self.graph.add_node(metric_id, kind="metric", value=value)
        self.graph.add_edge(company, metric_id, relation="HAS_METRIC")
    # Risk nodes, Appendix nodes, Document nodes...
```

**面试追问**：什么时候用 NetworkX 什么时候用 Neo4j？→ NetworkX 用于开发和演示——零配置，数据在进程内存中，适合单次分析。Neo4j 用于需要在多次分析间持久化知识积累的场景——比如每次分析的公司数据写入 Neo4j，后续分析可以直接查询已有数据而不需要重复获取行情。切换方式是设置 `MAS_NEO4J_URI` 环境变量，`graph.py:59-69` 的 `_build_knowledge_store()` 会优先尝试 Neo4j。

1. ## FastAPI 异步任务设计

**核心概念**：AI 分析任务的执行时间不可预测（取决于 LLM API 响应速度 + 分析复杂度），不适合在 HTTP 请求-响应周期内同步执行。异步任务设计的标准模式：① 客户端提交任务 → 立即返回 job_id（202 Accepted）；② 后台 worker 执行任务；③ 客户端轮询 job 状态直到完成。

任务队列的两种实现方式：轻量级的 FastAPI BackgroundTasks（在同一个进程中执行）和重量级的独立 Worker 进程（通过 Redis/RabbitMQ 解耦）。前者适合低并发、允许进程重启丢失任务的场景；后者适合生产环境的高并发和持久化需求。

**本项目**：`api/app.py` 暴露了三组端点：

1. **同步分析**：`POST /api/v1/analyze` — 直接执行完整流水线，返回结果。适合交互式使用和测试。
2. **异步提交**：`POST /api/v1/jobs` — `service.submit_job()` 创建数据库记录，`service.enqueue_job()` 尝试推入 Redis 队列。如果 Redis 不可用，使用 FastAPI BackgroundTasks 兜底。
3. **状态查询**：`GET /api/v1/jobs/{job_id}` — 从 SQLite 读取 job 状态和结果。

`worker.py:26-41` 的 `work_forever()` 是独立 worker 进程的入口——无限循环执行 `queue.dequeue(timeout_seconds=5)` 阻塞等待任务，收到任务后调用 `execute_analysis_job()`。使用 Redis BLPOP（阻塞左弹出）实现高效的任务等待，不消耗 CPU。

```Python
# api/app.py:114-135 — 异步任务提交def submit_job(payload, background_tasks, _=Depends(auth_dependency)):
    created = service.submit_job(query=payload.query, ...)
    queued = service.enqueue_job(created["job_id"], ...)
    if not queued:  # Redis 不可用时的降级路径
        background_tasks.add_task(service.run_job, ...)
    return SubmitJobResponse(**created, queue_backend="redis" if queued else "background-task")
```

**面试追问**：BackgroundTasks 和 Redis Worker 的主要区别是什么？→ BackgroundTasks 与 API 进程共享生命周期——API 进程重启，未完成的任务丢失。Redis Worker 是独立进程，API 重启不影响 Worker。但 Redis Worker 需要额外运维（启动 worker 进程、监控队列积压）。当前项目两种都支持，根据是否配置 `MAS_REDIS_URL` 自动选择。

1. ## PDF 财报解析与信息提取

**核心概念**：PDF 解析在金融场景中有两个层次的挑战：① 文本提取——PDF 的内部结构不保证文本顺序和可读性（特别是双栏布局和表格）；② 信息提取——从非结构化文本中识别公司名、财务指标和风险信号。

1. ## 情景分析与概率校准

**核心概念**：情景分析（Scenario Analysis）是投资研究的标配——分析师需要评估在不同宏观/行业条件下公司的表现范围。标准做法是定义三种情景：Base Case（基准，概率最高）、Bull Case（乐观）、Bear Case（悲观），每种情景附带收入增速和概率权重。

概率校准的关键在于：三种情景的概率之和必须等于 100%，且概率分配应该有数据依据而非拍脑袋。本项目用 EBITDA Margin 和 R&D Intensity 两个量化指标驱动概率分配——高利润率公司基准概率更高（确定性更强），高研发投入公司牛市概率更高（创新驱动的上行空间更大）。

**本项目**：`tools.py:402-422` 的 `generate_scenario_analysis()` 实现了数据驱动的概率校准：

- Base Case 概率固定 50%
- Bull Case 概率：R&D Intensity > 6% 时 30%，否则 20%（高研发→高创新上限→高牛市概率）
- Bear Case 概率 = 1.0 - Base - Bull（自动平衡到 20% 或 30%）

收入增速也由当前指标驱动：Base 增速 = 8%（高利润率）或 5%（一般利润率），Bull 增速 = Base × 1.8，Bear 增速 = Base × 0.3。

```Python
# tools.py:402-422 — 情景分析引擎def generate_scenario_analysis(metrics, company):
    ebitda_margin = metrics.get("ebitda_margin", 0.15)
    rd_intensity = metrics.get("r_and_d_intensity", 0.05)

    base_growth = 0.08 if ebitda_margin > 0.25 else 0.05
    bull_growth = base_growth * 1.8
    bear_growth = base_growth * 0.3

    bull_prob = 0.30 if rd_intensity > 0.06 else 0.20
    bear_prob = 1.0 - 0.50 - bull_prob
```

**面试追问**：为什么 Base Case 概率固定 50% 而不是根据公司实际情况动态调整？→ 这是一个简化假设。在真实投资分析中，Base Case 概率应根据盈利稳定性、行业周期性和宏观环境调整。当前固定 50% 是因为缺少历史波动率数据来做更精细的校准。如果接入 Bloomberg/Reuters 的数据接口，可以用历史 EPS 波动率反推概率分布。50% 是一个中性假设，对有经验的分析师来说一目了然。

1. ## Agent 审计与可追溯性

**核心概念**：在受监管的金融场景中，AI 系统的每一次分析决策都需要可追溯——监管机构可能要求回答"为什么这份报告建议增持 A 公司？"。Agent 审计的核心是记录：① 谁（哪个 Agent）② 在什么输入下 ③ 做了什么决策 ④ 输出了什么结果。

审计日志（Audit Log）不同于应用日志——应用日志面向开发者（debug 用），审计日志面向合规审查（证明决策合理性）。两者的结构和粒度不同：应用日志记录"调用了 DeepSeek API, latency=3.2s"，审计日志记录"Quant Agent: 基于 EBITDA Margin 34% 判定 Apple 盈利能力为 Strong"。

**本项目**：审计机制分布在三个层面：

1. **ReasoningMemory**（`memory.py:54-62`）：每个 Agent 函数在执行关键操作后调用 `self._record(step, status, detail)`，生成 `AuditEvent`（step/status/detail 三元组）
2. **SessionMemory**（`memory.py:11-19`）：每个 Agent 函数末尾调用 `self.session_memory.save()` 保存完整 state 快照
3. **导出**（`reporting.py:9-32`）：`export_run_artifacts()` 将 audit_log 序列化为 JSON，完整 state 也序列化——两份文件一起提供完整的决策溯源

```Python
# agents.py:41-46 — 审计记录机制def _record(self, step, status, detail):
    self.reasoning_memory.record(step=step, status=status, detail=detail)
    return {
        "audit_log": self.reasoning_memory.export(),
        "reasoning_memory": [
            f"{e['step']}::{e['status']}::{e['detail']}"for e in self.reasoning_memory.export()
        ],
    }
```

每个 Agent 函数的 detail 信息包含关键决策参数和数据量，例如 Supervisor 记录分析维度数量和公司数量，Quant 记录计算了多少个指标，Critic 记录综合风险评分。

**面试追问**：审计日志的 detail 字段是手动拼接的字符串，如果遗漏了关键信息怎么办？→ 确实，当前的审计信息由每个 Agent 开发者手动决定记录什么，容易被遗漏。更严谨的做法是在 Agent 基类中定义必须记录的字段（如输入 state 的哈希、关键决策参数的值），子类只能追加不能省略。不过以当前项目的 Agent 数量（7 个）和团队规模，手工记录的成本可控——每次写新 Agent 时审计日志是 checklist 的一项，而不是自动化机制。

1. ## 推理时 Agent vs 训练时 RL Agent

**核心概念**：在 LLM Agent 领域，目前有两条技术路线：① 推理时 Agent（Inference-Time Agent）——在模型推理阶段通过 prompt、工具调用、多步编排来实现复杂行为，模型权重不变；② 训练时 Agent（Training-Time Agent）——通过强化学习（RL）训练模型学会在特定环境中执行多步决策，模型权重被更新（如 Search-R1 的 GRPO 训练）。

两者的关键区别在于"智能"的来源：推理时 Agent 的智能来自 LLM 的通用能力 + 工程师设计的编排逻辑；训练时 Agent 的智能来自环境反馈对模型参数的优化。

**本项目**：Real-Finan 是一个纯粹的推理时 Agent 系统——所有 7 个 Agent 的"智能"来自 DeepSeek API + 我手写的编排规则（条件路由、阈值判断、因子映射）。系统不涉及任何模型训练或微调。这意味着系统的分析质量受两个因素约束：① DeepSeek 模型的基础能力；② 我设计的 prompt 和编排逻辑的质量。

选择推理时路线的原因是：金融分析任务的多样性（不同公司、不同分析角度、不同报告格式）使得为每种场景训练专用模型不现实，而推理时编排可以灵活适应不同需求——换个场景只需要改 Supervisor 的 prompt 和 Synthesizer 的报告模板。

**面试追问**：如果让你在某个环节引入 RL 训练，你会选哪个？→ Psychologist（情绪分析）。情绪分析的输入（管理层文本）和输出（语气标签+信心评分）相对结构化，可以构建标注数据集做有监督微调。Reward 函数可以基于"情绪判断与后续股价走势的一致性"来设计——但数据稀疏（财报一年四次），训练样本量是瓶颈。相比之下，Quant 的指标计算不需要 LLM，Critic 的评分规则需要可解释性（不适合黑盒训练）。

1. ## Prompt Engineering 在金融分析中的实践

**核心概念**：Prompt Engineering 不是简单的"写一段指令给 LLM"——在专业领域（如金融分析）中，有效的 prompt 需要包含三个要素：① 角色锚定（Persona）——告诉 LLM 它是谁（如"你是 Director of Research at an institutional investment firm"）；② 结构约束（Structure）——指定输出格式和推理步骤（如"第一步给结论，第二步给证据，第三步给投资含义"）；③ 参数调优（Parameter）——temperature 和 max_tokens 需要根据任务类型调整（创意型高 temperature，分析型低 temperature）。

**本项目**：系统中有 6 个不同的 prompt 模板，分布在不同的 Agent 中：

| Agent             | System Prompt 角色                                           | Temperature | Max Tokens | 关键策略            |
| ----------------- | ------------------------------------------------------------ | ----------- | ---------- | ------------------- |
| Supervisor        | "Supervisory Agent in enterprise multi-agent financial analysis system" | 0.1         | 300        | JSON 输出+维度定义  |
| Retrieval Profile | "equity research analyst"                                    | 0.2         | 280        | 中文输出+四段式     |
| Quant Peer        | "senior quantitative analyst"                                | 0.2         | 220        | 基于数据对比+中文   |
| Psychologist      | "管理层语气分析专家"                                         | 0.1         | 250        | JSON+0-10信心评分   |
| Critic Compliance | "financial compliance audit expert"                          | 0.1         | 220        | 三段式审计意见      |
| Synthesizer       | "Director of Research at institutional investment firm"      | 0.2         | 500        | 四段式摘要+数字驱动 |

一个关键的设计选择：所有金融分析型 prompt 用中文输出（因为最终报告面向中文读者），但角色锚定用英文职位（"Director of Research"比"研究总监"在 LLM 训练数据中有更丰富的金融分析语料关联）。

```Python

**面试追问**：为什么不同 Agent 的 temperature 值不同？→ temperature=0.1 用于需要结构化输出的任务（Supervisor 的 JSON、Critic 的审计意见）——需要确定性。temperature=0.2 用于需要分析判断的任务（Profile 生成、同行对标、报告摘要）——需要一定的表达多样性但分析框架稳定。没有用超过 0.2 的温度是因为金融分析对准确性要求高于创意性，"有洞察"的前提是"数据没错"。

## 一、项目基础（7题）

### Q1. 用一句话介绍你的项目

**参考答案：** Real-Finan 是一个基于 LangGraph 的多智能体金融分析系统——将投研分析拆解为 7 个专业化 Agent（Supervisor→Retrieval→Quant→Psychologist→Critic→Replanner→Synthesizer），通过条件路由实现自动化的数据融合、财务指标计算、情绪分析、风险评分和机构级报告生成。LLM 层用 DeepSeek API + 内置 local-fallback 做双链路容错，确保无 API 密钥也能跑通完整流水线。对外提供 FastAPI REST 接口，支持 PDF 财报上传和异步任务队列。

**面试官想听的点：** LangGraph, 7 Agent, 条件路由, 双链路容错, FastAPI, PDF解析, 不是简单的 ChatGPT wrapper

**常见踩坑：**

- 只说"用 AI 分析财报"——这没有体现工程复杂度,让面试官以为你是调了个 API 套壳。
- 说"集成了多个大模型"——实际只用了 DeepSeek 一个,fallback 是规则引擎不是其他模型,不要混淆概念。

### Q2. 为什么选择 LangGraph 而不是 LangChain Chain 或 AutoGPT？

**参考答案：** 三个原因。第一，我需要条件路由和循环——用户分析时可能缺数据需要回去重新检索,Chain 是纯线性 A→B→C,表达不了"如果缺数据就回去"的逻辑。第二，我需要确定性的控制流——金融分析的每个决策需要可审计,不能像 AutoGPT 那样把"下一步做什么"交给 LLM 判断,因为 LLM 给你的路由理由可能看起来合理但实际上是幻觉。第三，LangGraph 的 Checkpointer 自动保存每个节点执行后的 state 快照,我调试 7 个节点的流水线时可以直接回溯到任意节点的中间状态——这在手写状态机里需要自己实现全套序列化和恢复逻辑。

如果我不用 LangGraph,最可能的选择是自己写一个状态机循环: `while not done: state = execute_next(state)`。这在 2-3 个节点时可行,但 7 个节点加 4 条条件路由时,手写的 if-else 嵌套会成为维护噩梦。LangGraph 的 StateGraph 在 `graph.py:71-106` 只用了 36 行代码表达了所有这些逻辑。

**面试官想听的点：** 条件路由不是线性,确定性控制流 vs LLM驱动,Checkpointer的价值,手写状态机的局限

**常见踩坑：**

- 说"因为 LangGraph 是主流框架"——面试官想知道你为什么选它,不是别人为什么选它。
- 说"AutoGPT 不够灵活"——太笼统,要说清楚具体什么场景不灵活。

### Q3. 7 个 Agent 的分工依据是什么？

**参考答案：** 我是按照真实投研团队的角色分工来拆解的。一个买方研究团队做公司深度分析时,典型的分工是: 分析师收集数据(Retrieval) → 财务建模(Quant) → 管理层评估(Psychologist) → 风险审查(Critic) → 撰写报告(Synthesizer)。我为这个流程加了两个额外的 Agent: Supervisor 在入口处做任务理解和公司识别——这对应团队里的研究总监;Replanner 在数据不足时触发重试和降级——这对应团队里的项目经理。

关键是每个 Agent 的职责边界要清晰——不能出现"Retrieval 做了一点计算,Quant 又去取数据"这种混乱。我通过 `FinanceState` 的字段归属来保证这一点: `retrieved_docs` 只在 Retrieval 中写入,`financial_metrics` 只在 Quant 中写入,`sentiment_analysis` 只在 Psychologist 中写入。每个 Agent 的产出字段在 TypedDict 中有明确的所有者。

**面试官想听的点：** 对应真实团队分工,Supervisor+Replanner是额外角色,字段归属清晰,TypedDict

**常见踩坑：**

- 说"7 是随便定的"——面试官会觉得你在瞎设计。
- 把 Retrieval 说成"数据预处理"——低估了多源融合的复杂度。

### Q4. 你这个项目的最大技术难点是什么？

**参考答案：** 不是某个算法或模型,而是让整个 7-Agent 流水线在数据质量参差不齐的情况下仍然产出可读的报告。具体来说有三个场景: ① PDF 是用户上传的空文件或扫描质量很差的文档——PyMuPDF 可能提取不到文本;② YFinance 在非美股交易时段返回空数据或部分字段为 null;③ DeepSeek API 返回的 JSON 被 Markdown 代码块包裹导致 `json.loads()` 失败。

我的解决思路是"每个环节都有兜底,兜底不是返回错误,而是返回一个合理的降级结果"。LLM JSON 解析用 `parse_with_fallback()` (`tools.py:425-430`) 自动剥 Markdown fences;市场数据获取在 Yahoo 失败时返回全 None 的结构化字典而非抛异常 (`market_data.py:40-54`);Synthesizer 在数据不足时不输出"数据不足无法分析",而是加 `knowledge_hint` 提示 LLM 用公开知识补充 (`agents.py:419-422`)。

这些处理看起来很 defensive,但正是这些 5-10 行的兜底逻辑保证了系统的鲁棒性。面试官如果让我重来一次,我会在系统入口处加一个数据完整性评分,让用户在分析前就知道数据质量——而不是让系统在内部默默降级。

**面试官想听的点：** 具体的问题场景+具体的代码位置+具体的解决方式,不是在说抽象的空话

**常见踩坑：**

- 说"准确率不够"——这个项目没有 ground truth label,不存在"准确率"。
- 说"性能优化"——LLM API 延迟是瓶颈,代码层面的性能不是主要矛盾。

### Q5. 你项目里有 30+ 状态的 TypedDict,为什么不直接用 Pydantic？

**参考答案：** 因为 LangGraph 原生支持 TypedDict 做 StateGraph 的泛型参数——`StateGraph(FinanceState)`——框架会根据 TypedDict 的键名做增量合并。如果用 Pydantic BaseModel,我需要自己处理状态合并逻辑（Pydantic model 的 `dict()` 再 merge 再 `parse_obj()` 成本高）。

另一个更实际的原因: `total=False` 让所有字段可选。在 7 个节点的执行流中,不同节点逐步填充不同字段——Supervisor 填充 `companies`/`plan`,Retrieval 填充 `retrieved_docs`,Quant 填充 `financial_metrics`。Pydantic 的 `Optional` 也能表达同样语义,但 TypedDict 更轻量且 LangGraph 文档里的所有示例都用 TypedDict,遵循框架惯例减少踩坑。

**面试官想听的点：** LangGraph 原生支持,`total=False`,增量合并,框架惯例

**常见踩坑：**

- 说"TypedDict 比 Pydantic 好"——两者适用场景不同,Pydantic 更适合 API 层的数据校验（`schemas.py` 里用的就是 Pydantic）。

### Q6. 如果你要把这个项目做成一个 SaaS 产品,需要加什么？

**参考答案：** 三件事。第一，用户管理和多租户——当前 `FinanceMultiAgentSystem` 是无状态的（除了 InMemorySaver），多个用户请求会互相覆盖 thread_id。需要给每个用户独立的 checkpointer 和 session 隔离。第二，结果缓存——对同一家公司同一季度的分析结果可以缓存,避免重复调用 LLM 和行情 API。可以用 Redis 做 key-value 缓存,key 是 `company:quarter:analysis_type` 的哈希。第三，流式输出——当前是整个流水线跑完再返回结果,用户等 15-25 秒看到完整报告。改为 SSE 流式传输每个 Agent 的完成状态,用户可以逐步看到"正在识别公司...→ 正在获取市场数据...→ 正在计算指标..."的进度。

技术层面还有: 改 InMemorySaver 为 SqliteSaver 或 PostgresSaver 以支持持久化和分布式部署;加 API 限流和用量计费;把 LocalFallbackLLMClient 的预设文本改成可配置的模板（不同租户可能需要不同风格的 fallback 文本）。

**面试官想听的点：** 多租户,缓存,流式输出,持久化,限流。从单用户 demo → 多租户 SaaS 的思考。

**常见踩坑：**

- 只说"加用户登录"——太浅,鉴权已经有了（`auth.py`），缺的是多租户隔离。
- 说"加更多公司数据"——这不是技术架构问题,是数据采购问题。

### Q7. 你项目里哪个部分是自己最满意的？

**参考答案：** `ResilientLLMClient` (`llm.py:89-104`)。代码只有 16 行,但它解决了"有 API 密钥时用 DeepSeek,没有时也能跑"这个实际体验问题。我见过很多 AI demo 项目——clone 下来要配 API 密钥,配完了跑不通因为密钥过期或额度用完,然后就放弃了。我这个 `ResilientLLMClient` 的 fallback 不是返回空字符串或错误信息,而是根据 prompt 关键词返回预设的中文分析文本——这些文本是基于 Apple 和 Microsoft 的真实对比数据写的,所以本地 demo 跑出来的报告读起来是逻辑自洽的。

技术上它是一个代理模式的简单实现,但设计理念值得说: 降级不是妥协,降级输出的质量决定了用户在没有外部依赖时对系统的第一印象。面试官如果让我展开,我会说这个模式可以推广到任何依赖外部 API 的 AI 系统——为每种 prompt 类型维护一个 fallback 响应模板,确保核心体验不因外部依赖故障而中断。

**面试官想听的点：** 具体代码行数,解决的是用户体验问题,模式可推广

**常见踩坑：**

- 说"整个架构设计"——太泛。
- 说"Quant 的 AST 求值器"——60 行代码虽然精巧但技术深度不够撑起"最满意"。

## 二、Agent 编排与路由（7题）

### Q8. 条件路由的判断逻辑为什么不交给 LLM？

**参考答案：** 四个路由函数 (`graph.py:21-35`) 全部是纯 Python 的条件判断: 检查 `state.get("replan_reason")` 是否为 None,检查 `state.get("degraded_mode")` 是否为 True。不走 LLM 的原因是: ① 延迟——LLM 判断需要一次 API 调用(1-3秒),纯 Python 判断零延迟;② 确定性——`replan_reason` 有值就代表需要重规划,不存在"可能有值但不需要"的模糊地带,不需要 LLM 来做语义判断;③ 可测试——纯函数路由可以直接用单元测试验证,LLM 路由的测试需要 mock API。

AutoGPT 式 LLM 路由的典型问题是: LLM 可能给出一个看起来合理但实际错误的路由理由——比如"数据已经完整了,但为了更全面,建议再检索一次"——这在对话型 Agent 中可以接受,在金融分析中需要为每一次路由决策提供确切的审计理由。

**面试官想听的点：** 延迟+确定性+可测试性,LLM路由的问题(幻觉理由),金融场景的可审计性

**常见踩坑：**

- 说"LLM 不够聪明"——不是聪明不聪明的问题,是确定性 vs 概率性的设计选择。

### Q9. Replanner 的 degraded_mode 触发后,Synthesizer 如何处理数据缺失？

**参考答案：** 降级模式的核心逻辑在 Synthesizer 的 `knowledge_hint` (`agents.py:419-422`)。当 `has_metrics` 为 False 且没有 PDF 文档上下文时,给 LLM 的 prompt 追加一段特殊提示: "Limited structured data available. Leverage your public knowledge of these companies to provide insightful analysis. Do not simply state 'insufficient data'."

这个设计有两个意图: ① 不让 LLM 输出"数据不足无法分析"——这在产品层面是死胡同;② 明确区分"系统分析了数据"vs"系统用了公开知识"——报告的 Methodology 章节会说明数据来源,用户能判断分析的依据质量。

降级模式下生成的报告中,Financial Performance Analysis 部分会显示 `[Degraded Analysis]` 标记 (`agents.py:556`),提醒读者这部分不是基于结构化数据计算的。

**面试官想听的点：** `knowledge_hint` 的具体内容,区分数据和公开知识,`[Degraded Analysis]` 标记

**常见踩坑：**

- 说"降级后报告质量会差一些"——废话,要说具体哪里会差(SWOT 和投资论点仍然有内容,但财务指标章节没有具体数值)。

### Q10. 7 个 Agent 的执行顺序是固定的吗？有没有动态跳过的情况？

**参考答案：** 当前执行顺序固定: START → Supervisor → Retrieval → (Quant | Replanner) → (Psychologist | Replanner) → Critic → Synthesizer → END。没有 Agent 被完全跳过,但个别 Agent 内部有短路逻辑:

- Quant 在 `replan_reason` 有值时直接返回空 `financial_metrics` (`agents.py:196-198`),不执行计算
- Replanner 不是每次都被触发——只有当 Retrieval 或 Quant 设置了 `replan_reason` 时才路由到它

所以严谨的说法是: 所有 Agent 节点都在图中,但不是所有节点在每次执行中都会做有意义的工作。如果把"跳过"定义为节点内部 return early,那么 Quant 可能被"软跳过";如果把"跳过"定义为不经过节点,那么 Replanner 可能被"硬跳过"。

如果要做动态图构建(根据 query 类型决定哪些 Agent 参与),可以在 `_build_graph()` 之前根据 query 分析结果决定注册哪些节点。但当前没有这个需求——金融分析的标准化流程需要的维度是固定的。

**面试官想听的点：** 短路逻辑 vs 硬跳过,Replanner 的条件性,动态图构建的可行性

**常见踩坑：**

- 说"可以动态跳过"但在代码里找不到对应逻辑——要区分"设计上可以"和"代码里已经做了"。

### Q11. 如何保证 Agent 之间的状态一致性？如果两个 Agent 同时修改同一个字段怎么办？

**参考答案：** 首先,当前架构中 Agent 是顺序执行的(StateGraph 的节点串行),不存在并发修改同一个字段的问题。其次,我有意做了字段归属设计——每个字段只有一个"写入者":

- `companies`/`plan`/`task_brief` → 只在 Supervisor 写入
- `retrieved_docs`/`market_snapshots`/`company_profiles` → 只在 Retrieval 写入
- `financial_metrics`/`peer_comparison` → 只在 Quant 写入
- `sentiment_analysis` → 只在 Psychologist 写入
- `compliance_findings`/`compliance_summary`/`risk_scores` → 只在 Critic 写入
- `final_report`/`executive_summary`/`swot_analysis`/`investment_thesis` → 只在 Synthesizer 写入
- `retries`/`degraded_mode`/`appendix_search_done` → 只在 Replanner 写入

LangGraph 的增量合并只是简单的字典 update,不做冲突检测。如果未来改成并行执行(如 Psychologist 和 Quant 对不同公司的分析可以并行),需要引入字段锁或分区状态——按公司拆分 state,每个并行 worker 只写自己公司的子字典,最后 merge。当前没有做是因为 7 个节点串行执行的总时间被 LLM API 延迟主导,并行化的收益有限。

**面试官想听的点：** 字段写入者隔离,并行化的可能性和限制,增量合并的局限

**常见踩坑：**

- 说"LangGraph 自动处理并发"——LangGraph 默认串行,并发需要显式配置。

### Q12. 为什么 Supervisor 放在第一个而不是让 Retrieval 直接开始？

**参考答案：** Supervisor 的核心职责不是数据获取而是"问题理解"——用户 query 可能是"比较 Apple 和 Microsoft 的研发投入趋势"也可能是"分析这几份 PDF 里的公司财务风险"。Supervisor 需要做三件事: ① 从 query 和 PDF 中识别出具体要分析哪些公司 (`extract_companies_from_query()`);② 定义分析维度和关键问题（通过 LLM 生成 task_brief);③ 确定执行计划（5 个 Phase 的蓝图）。

如果没有 Supervisor 直接进 Retrieval,Retrieval 面对一个模糊的 query 时需要自己做公司识别和维度定义——这混淆了"规划"和"执行"的职责。类比真实团队: 你不会让负责收集数据的分析师同时决定分析框架——那是研究总监的职责。

另外,Supervisor 的 `extract_companies_from_query()` (`tools.py:158-212`) 有四级回退策略（样本数据→已知别名→LLM 提取→PDF 文件名）,这个逻辑放在专门的入口节点比混在 Retrieval 里更清晰。

**面试官想听的点：** 职责分离（规划 vs 执行）,四级公司识别策略,类比真实团队

**常见踩坑：**

- 说"因为 LangGraph 要求从 START 开始"——这只是框架约定,不是设计理由。

### Q13. 如果要在现有 7 个 Agent 的基础上新增一个"ESG 分析 Agent",应该如何插入？

**参考答案：** 分四步。第一步: 在 `FinanceState` 中新增 ESG 相关字段,如 `esg_scores: dict[str, dict[str, float]]` 和 `esg_summary: str`。第二步: 在 `AgentRuntime` 中实现 `esg_analyst(self, state) -> FinanceState` 方法,包括 ESG 数据获取（需新增数据源）和处理逻辑。第三步: 在 `_build_graph()` (`graph.py:71-106`) 中注册节点,决定它放在哪个位置——ESG 分析需要财务数据（Quant 之后）和供应链数据（Retrieval 已有）,逻辑上放在 Critic 之前或与 Critic 平级都可以。如果和 Critic 平级,将 Critic 后的边改为先经过 ESG 再进 Synthesizer。第四步: 在 Synthesizer 的报告模板中新增 ESG 章节,在 Executive Summary 的 prompt 中追加 ESG 分析内容的要求。

扩展的关键挑战是数据源——ESG 评分不像股价那样有免费的公开 API。可能的方案: 在 Retrieval 阶段增加 ESG 关键词的 PDF 搜索（sustainability, carbon, governance 等关键词计数）,作为内部 ESG 信号的代理变量。

**面试官想听的点：** 四个步骤（State→Agent→Graph→Report）,数据源挑战,扩展的具体位置

**常见踩坑：**

- 说"加个 Agent 很容易"但没有具体步骤——扩展性不是说说的。
- 忽略了数据源接入是最大挑战而非代码改动。

## 三、金融计算与风险（6题）

### Q14. 为什么用 AST 而不是 `eval()` 或正则表达式来实现公式求值？

**参考答案：** `eval()` 是安全红线——即使你说"只在内部使用",代码审查也过不了。正则表达式能处理 `ebitda / revenue` 这种简单公式,但遇到 `(ebitda - operating_income) / revenue` 这种带括号的嵌套表达式就捉襟见肘——你需要写一个完整的表达式解析器,而 Python 的 `ast` 模块正好是一个现成的、经过充分测试的表达式解析器。

我选择 `ast.NodeVisitor` + 白名单的模式 (`tools.py:13-69`),本质上是复用了 Python 的 parser 和 AST 结构,同时通过白名单物理隔绝了任意代码执行的可能。白名单只放行 7 大类节点: `Expression, BinOp, Add, Sub, Mult, Div, Pow, Name, Constant, UnaryOp, USub`。任何函数调用（`Call` 节点）、属性访问（`Attribute` 节点）、下标访问（`Subscript` 节点）都会在 `visit()` 入口处被拦截。

对比使用 `eval()`: 同样 3 行代码,但安全边界完全不同。对比使用正则: 只能处理简单情况,扩展性差。AST 方案在 60 行代码内同时实现了安全性、可扩展性和正确性。

**面试官想听的点：** eval()安全红线,正则的局限,白名单机制的物理安全性,60行的实现成本

**常见踩坑：**

- 说"eval() 不安全所以没用"——面试官要听你选了什么的 WHY,不是没选什么的 WHY。
- 说"正则表达式就够了"——试试写一个匹配嵌套括号的正则就明白了。

### Q15. 五维财务指标体系中,R&D Intensity 为什么重要？

**参考答案：** R&D Intensity（研发投入强度 = R&D / Revenue）衡量的是公司对未来增长的投入意愿和能力。在科技行业,这个指标比当前利润率更能预示未来 3-5 年的竞争力轨迹。在我的系统中,R&D Intensity 影响三个地方:

1. **Quant 分析**: 作为五大核心指标之一直接计算和展示
2. **情景分析**: R&D Intensity > 6% → Bull Case 概率从 20% 提升到 30%——因为高研发投入为技术创新驱动的超预期增长提供了基础 (`tools.py:411`)
3. **SWOT**: R&D Intensity > 5% → Strengths 中增加"Abbove-peer R&D investment sustaining innovation pipeline" (`agents.py:620`)

但如果只看 R&D Intensity 不看 EBITDA Margin 会得出错误结论——一家公司可以大手笔投入研发但烧钱速度超过赚钱速度。所以系统中这两个指标是联合解读的: 高 Margin + 高 R&D = 健康创新; 低 Margin + 高 R&D = 可能是烧钱换增长; 高 Margin + 低 R&D = 吃老本的风险。

**面试官想听的点：** 不只定义指标,还说它在系统中被用在哪里,和其他指标的联动

**常见踩坑：**

- 只说"衡量创新能力"——没说在系统中怎么用,等于背教科书。

### Q16. 风险评分的校准依据是什么？

**参考答案：** 当前的风险评分模型 (`agents.py:331-352`) 使用线性映射和离散查表两种校准方式:

- **线性映射**: 财务风险 = `9.0 - ebitda_margin × 15`。选择斜率 15 是为了让 margin 在 0%-60% 范围内映射到 1.5-9.5 区间。这个"15"是基于常识校准的——EBITDA Margin 每下降 1 个百分点,财务风险上升 0.15 分,对于分析师的直觉来说这个量级是合理的。
- **离散查表**: 供应链风险直接映射（low=2.0, medium=5.0, high=8.0）。这些阈值来自行业惯例——低风险供应商多元化,中风险有一定集中度,高风险单一依赖。
- **加性因子**: 运营风险 = 供应链基线 + 情绪风险标记数 × 0.6。这个 0.6 的权重是我主观设定的——每个风险标记增加约半个点的运营风险,因为情绪分析中的风险标记通常是值得关注的信号而非决定性因素。

我承认这些校准是经验性的而非数据驱动的。如果有历史数据（如过去的风险评分与实际发生的风险事件的对应关系）,可以用 logistic 回归或分位数映射来做更科学的校准。在项目文档中我没有隐藏这一点——所有阈值和映射关系都直接写在代码里,可审查可调整。

**面试官想听的点：** 具体的数字来源(为什么是15/0.6),承认经验校准的局限,改进方向

**常见踩坑：**

- 说"基于专家经验"——太虚,要说具体数字和推导逻辑。
- 说"用了机器学习模型"——代码里没有,不要编。

### Q17. 供应链风险等级（low/medium/high）是如何确定的？

**参考答案：** 来自三个渠道,按优先级排列:

1. **内置样本数据**: Apple 的 `supply_chain.risk_level` 是 "medium" (因为大中华区制造集中),Microsoft 是 "low" (云基础设施采购多元化)。这些是我根据公开信息预设的 (`sample_financial_data.py:10-42`)。
2. **PDF 文本信号**: `documents.py:132-139` 在全文搜索 `supply chain risk`/`供应链风险`/`supply constraint`/`logistics` 关键词。如果检测到相关讨论,设置为 "medium"。这是基于"有供应链讨论 = 至少存在一定关注度"的假设。
3. **默认值**: 如果以上两个渠道都没有信号,在 `retrieve_company_payload()` 中返回 "unknown" (`tools.py:148`)。但在 Retrieval Agent 中,如果有 PDF source documents 且 risk_level 为 unknown,会检测文档内容中是否包含 "risk" 关键词,有则设为 "medium" 无则设为 "low" (`agents.py:149-151`)。

这个系统最明显的局限是: PDF 中出现 "supply chain" 一词不代表一定有风险——可能是公司在说"我们供应链管理做得很好"。目前没有区分正面/负面上下文,这是 NLP 层面的改进方向。

**面试官想听的点：** 三级确定逻辑,每级的代码位置,已知局限和改进方向

**常见踩坑：**

- 说"LLM 分析的"——不是,这是规则引擎。

### Q18. 情景分析中,Bull/Bear Case 的增速是如何推导的？

**参考答案：** `tools.py:402-422` 的 `generate_scenario_analysis()` 使用两步推导:

1. **Base 增速**: EBITDA Margin > 25% → 8%,否则 5%。逻辑是高利润率公司通常有更强的定价权和市场份额,在常态经济环境下增速更高。
2. **Bull/Bear 增速**: Bull = Base × 1.8, Bear = Base × 0.3。这个 1.8 和 0.3 的乘数是经验值——1.8 倍意味着乐观情景下增速接近翻倍（对于科技公司,创新突破带来的加速可以支撑这个量级）,0.3 倍意味着悲观情景下仍保持正增长（对于 Apple/Microsoft 这类头部公司,全面衰退的概率低于零增长）。

概率分配: Base 固定 50%,Bull = R&D Intensity > 6% 时 30% 否则 20%,Bear 自动补齐到 100%。

这个模型是最简化版本的——它只有一个驱动变量（EBITDA Margin）和一个调节变量（R&D Intensity）。真实投资分析的情景推演通常至少包含: 宏观 GDP 假设、行业增速假设、市场份额变化假设、利润率变化假设四个维度。当前简化是因为没有接入宏观经济预测数据。

**面试官想听的点：** 乘数的选择理由,承认简化,改进方向

**常见踩坑：**

- 说"用蒙特卡洛模拟"——代码里没有,不要过度包装。
- 不解释为什么是 1.8 不是 2.0——面试官会追问。

### Q19. 如果一家公司的财务数据完全不在系统里,Quant Agent 如何处理？

**参考答案：** 流程是: Retrieval 阶段,`retrieve_company_payload()` 检查样本数据——不在→检查 PDF 提取——没有相关文档→返回空的 `market_data` 和 `"unknown"` 的 `supply_chain`。但 Retrieval 仍然会调用 `market_data_client.fetch_company_snapshot()` 获取 yfinance 数据——只要用户 query 中的公司名能映射到股票代码,实时行情数据（股价/PE/市值）仍然可以获得。

Quant 阶段,`agents.py:209-229` 的基础数据字典 `base_data` 需要至少 3 个财务指标（revenue/ebitda/r_and_d/operating_income）,如果不满足→不会触发核心指标计算。但 Quant 仍然会从 `live_market` 中提取可用的市场数据（PE/市值/月回报/52周位置）。

所以完整路径是: 样本数据→PDF 提取→实时行情→LLM 公开知识四级降级,确保无论数据多稀疏都能产出有内容的报告。

**面试官想听的点：** 四级降级链路,每个环节能提供什么数据,最终不会输出空报告

**常见踩坑：**

- 说"会提示数据不足"——这是产品缺陷,不是答案。

## 四、LLM 工程（6题）

### Q20. 为什么选择 DeepSeek 而不是 GPT-4 或 Claude？

**参考答案：** 三个实际原因,没有技术宗教因素。第一,DeepSeek API 的定价大约是 GPT-4 的 1/10——这个项目每次分析要调用 4-6 次 LLM,在开发阶段我跑了上百次测试,用 GPT-4 的成本会很高。第二,DeepSeek 的中文能力在金融文本分析场景下表现不错——输出的中文分析在术语准确性和表达流畅度上能满足需求。第三,我在 `LLMSettings.from_env()` (`llm.py:18-28`) 中把所有模型参数（base_url/model/timeout）做成环境变量配置,换模型只需要改两个环境变量——没有和 DeepSeek 做深度绑定。

如果面试官问 GPT-4 有没有什么 DeepSeek 做不到的——金融合规审计场景下,GPT-4 对监管术语（如 SEC Regulation S-K, ESMA 披露要求）的知识更全面。但当前项目的合规审计是通用性的（检查是否有风险免责声明和数据来源标注）,DeepSeek 完全够用。

**面试官想听的点：** 成本+中文能力+可替换性,不是品牌偏好,承认不同模型的差异

**常见踩坑：**

- 说"DeepSeek 最好"——模型选择是 tradeoff,不是排名。
- 没提到环境变量配置让模型可替换——这是工程亮点。

### Q21. `ResilientLLMClient` 为什么 `except Exception` 而不是捕获更具体的异常？

**参考答案：** 对于上层 Agent (`AgentRuntime` 的各个方法)来说,LLM 调用失败的原因不重要——网络超时、认证失败、返回格式错误的结果都一样: "LLM 不可用,用 fallback"。`except Exception` 的宽泛捕获是故意为之——我不想让上层的每个 Agent 调用方都要处理 `httpx.TimeoutException`、`httpx.HTTPStatusError`、`json.JSONDecodeError` 等多种异常类型。

但有一个代价: `except Exception` 会吞掉 bug。如果 `DeepSeekChatClient.chat()` 里有一个 `AttributeError`（比如拼错了变量名）,它也会被捕获并静默切换 fallback,导致开发阶段难以发现这类错误。改进方案: 在生产代码中区分"预期异常"(网络/API/解析错误→切 fallback)和"非预期异常"(代码 bug→抛出)。可以维护一个 `RETRYABLE_EXCEPTIONS` 元组,只捕获这些类型,其他重新 raise。

**面试官想听的点：** 上层调用的简单性,吞bug的代价,改进方案(区分预期vs非预期)

**常见踩坑：**

- 说"为了代码简洁"——这是副作用,不是设计理由。
- 说"应该只捕获 httpx 的异常"——这没考虑 JSON 解析失败的情况。

### Q22. `LocalFallbackLLMClient` 的预设文本是如何设计的？

**参考答案：** `llm.py:66-86`。它不是随机返回 text,而是根据 prompt 中的关键词做语义匹配:

- `task_brief` 或 `任务概括` → 返回 Apple+Microsoft 对比分析的 JSON 格式 task_brief
- `executive summary` 或 `执行摘要` → 返回一段基于真实对比数据的摘要（Apple 供应链风险高于 Microsoft,但 Microsoft 研发投入更高）
- `合规` 或 `compliance` → 返回合规审计通过的意见
- 其他 → 返回通用占位文本

这些预设文本是在开发阶段基于实际跑 DeepSeek 的输出结果总结的——它们不是凭空编造,而是对"一个好的 LLM 在此场景下会输出什么"的近似。关键设计: 每个预设文本都基于 Apple/Microsoft 的真实数据关系（如"Apple 供应链风险更高"这个判断在样本数据中可以验证——Apple 的 supply_chain.risk_level 是 medium,Microsoft 是 low）。

**面试官想听的点：** 关键词匹配逻辑,预设文本的数据依据,不是随机占位符

**常见踩坑：**

- 说"随便写了几句"——这会让人质疑 fallback 的严肃性。
- 没注意到预设文本中有真实数据可验证的判断。

### Q23. 不同 Agent 的 temperature 值为什么不同？

**参考答案：** 三个温度档位对应三种任务类型:

| 场景                                                 | Temperature | 原因                                      |
| ---------------------------------------------------- | ----------- | ----------------------------------------- |
| Supervisor JSON / Critic 合规 / Psychologist JSON    | 0.1         | 需要结构化输出,低温度减少格式错误         |
| Retrieval Profile / Quant Peer / Synthesizer Summary | 0.2         | 需要分析判断和表达多样性,但不能偏离事实   |
| (无)                                                 | -           | 没有超过 0.2 的场景——金融分析不需要创意性 |

temperature=0.1 接近贪婪解码——LLM 选择概率最高的 token,适合"格式比内容重要"的场景。temperature=0.2 给了一定的表达空间——"Director of Research"写的摘要可以有不同的措辞,但分析框架必须一致。

一个实践细节: Supervisor 和 Psychologist 都要求 JSON 输出,但 Supervisor 用 0.1,Psychologist 用 0.2——因为 Psychologist 的 JSON 包含主观判断字段（`key_themes`/`risk_flags`/`strategic_priority`）,稍微高一点的温度可以让 LLM 不总给相同的主题和风险标记。

**面试官想听的点：** 三档划分,JSON vs 分析型的温度差异,没有超过0.2

**常见踩坑：**

- 说"temperature 越低越准确"——这是一种误解,低 temperature 只是减少随机性,数据本身错误时低温度反而更稳定地错。

### Q24. LLM 返回 JSON 被 Markdown 代码块包裹的问题怎么处理的？

**参考答案：** 这是每个接入 LLM 的开发者都会遇到的痛点——prompt 里说"只返回 JSON",LLM 还是会包一层 ````json ... ````。我的处理方式在 `tools.py:425-430` 的 `parse_with_fallback()`:

```Python
def parse_with_fallback(text: str) -> dict[str, Any]:
    clean = text.strip()
    if clean.startswith("```"):
        clean = clean.split("\n", 1)[-1].rsplit("\n", 1)[0]
    return json.loads(clean)
```

逻辑: 检测首字符是否为 ``` → 去掉首行和末行 → `json.loads()`。这个处理覆盖了 90% 的包裹情况,但有两个 corner case: ① LLM 在 code fence 前后加了额外文字（如 "here is the json: `json ... `hope this helps"）——当前逻辑会挂；② LLM 输出了合法的 JSON 但 key 不是英文双引号（如中文引号或单引号）——`json.loads()` 挂。

改进方向: 用正则提取 code fence 内的内容（`re.search(r'```(?:json)?\s*\n(.*?)\n```', text, re.DOTALL)`）比 split 更鲁棒。对于非标准引号,可以在 `json.loads()` 失败后用 `json5` 库做宽松解析。

**面试官想听的点：** 90% 覆盖率的处理,两个 corner case,改进方案

**常见踩坑：**

- 只说"做了处理"——要说具体怎么处理的,覆盖了哪些情况。
- 说"LLM 不应该返回 code fence"——这是理想主义,现实调试中 LLM 就是会这样。

### Q25. 如果让你优化 LLM 调用的延迟,你会怎么做？

**参考答案：** 当前的 4-6 次 LLM 调用全部是串行的,这是延迟的主要来源。优化分三个层次:

**短期（不改架构）**: ① 降低部分 Agent 的 max_tokens——Supervisor 的 300 和 Psychologist 的 250 可以降到 200 够用；② 为重复性调用加缓存——同一家公司同一个季度的 Profile 生成不需要每次调 LLM,用 company+timestamp 做 key 缓存结果。

**中期（并行化）**: Retrieval 阶段的每家公司 Profile 生成（`agents.py:161-167`）可以并行——N 家公司同时调 LLM,理论上延迟从 N×T 降到 max(T)。Quant 阶段的 peer_comparison 和 Psychologist 的情绪分析也可以并行——两者不依赖彼此的输出。实现方式: `asyncio.gather()` 或 `concurrent.futures.ThreadPoolExecutor`。

**长期（架构调整）**: 把一些 LLM 调用替换为更轻量的操作——Supervisor 的公司识别已经有四级规则回退,实际很少走到 LLM 那步；Critic 的合规审计可以改成模板化输出（大部分分析场景的合规意见是相似的）,只有遇到异常的 compliance_findings 时才调 LLM。

**面试官想听的点：** 短期/中期/长期的分层思考,具体的优化数字(from N×T 到 max(T)),替换 LLM 调用为规则

**常见踩坑：**

- 只说"并行化"没有具体说哪些 Agent 可以并行——需要基于数据依赖分析。
- 说"换更快的模型"——这不算工程优化。

## 五、工程化（6题）

### Q26. 为什么同时支持同步 API 和异步任务队列？

**参考答案：** 两种模式适用不同场景。同步 API (`POST /api/v1/analyze`) 适合: 开发调试、内部工具、单次交互式分析——用户发送 query,等待 15-25 秒后得到完整报告。异步任务队列 (`POST /api/v1/jobs`) 适合: 批量分析、Web 前端提交后轮询、需要失败重试和状态追踪的生产场景。

架构上两者复用同一个 `FinanceAnalysisService`——`analyze()` 方法被两种路径调用 (`service.py:20-46`)。区别在于调用方式: 同步路径是 HTTP 请求线程直接调用；异步路径是 Redis Worker (`worker.py:26-41`) 或 FastAPI BackgroundTasks 调用。

一个值得说的设计: 异步任务的路由也做了降级——`api/app.py:121-128` 中先尝试推入 Redis 队列,如果 Redis 不可用（`MAS_REDIS_URL` 未配置或连接失败）,自动退化为 BackgroundTasks。这意味着部署者不需要 Redis 也能跑异步任务（虽然进程重启会丢任务）。

**面试官想听的点：** 两种模式的不同场景,共享同一个 Service 方法,Redis→BackgroundTasks 的降级

**常见踩坑：**

- 说"异步更好"——两种各有场景,没有绝对的好坏。

### Q27. 数据库设计为什么选择 SQLAlchemy + SQLite？

**参考答案：** `database.py:13-105`。SQLAlchemy ORM 的选择是因为它提供了一层数据库抽象——开发阶段用 SQLite（零配置,文件即数据库）,生产部署改环境变量即可切换到 PostgreSQL。`Base.metadata.create_all(self.engine)` 自动建表,不需要手动写 DDL。

`AnalysisJob` 表的字段设计反映了任务的生命周期: `status`（pending→running→completed/failed）追踪执行状态,`result_json`/`artifacts_json` 存储结果（TEXT 列存 JSON 字符串,不做关系型展开）,`error_message` 只在失败时填充。之所以用 JSON 列而不是对分析结果做关系型建模——分析结果的结构高度可变（指标数量、公司数量、报告长度都不确定）,JSON 列更自然。

**面试官想听的点：** SQLite→PostgreSQL 可切换,ORM 抽象,JSON 列的理由

**常见踩坑：**

- 说"SQLite 够用了"——对于生产多并发场景 SQLite 的写锁是瓶颈,要体现出知道这一点。

### Q28. Redis 队列用的是 BLPOP/RPUSH,为什么不用更成熟的任务队列框架（如 Celery）？

**参考答案：** `queueing.py:9-25`。用原始 BLPOP/RPUSH 而不是 Celery/RQ 等框架,是因为这个项目的队列需求极其简单——单队列、无优先级、无定时任务、无结果回传。Celery 的配置复杂度（broker URL、result backend、序列化方式、worker 参数）对于"推一个 JSON 任务,worker 取出来执行"的场景是过度设计。

但我也意识到了局限——当前 `RedisQueueManager` 没有消息确认机制（acknowledgement）。如果 worker 在 `execute_analysis_job()` 执行过程中崩溃,任务就丢失了（因为 BLPOP 已经移除了消息）。Celery 的 ACK 机制可以保证任务至少在 worker 崩溃后被重新投递。如果这个项目要上生产,我会在 `dequeue()` 中改用 BRPOPLPUSH 做可靠队列模式（从主队列 pop 后先 push 到备份队列,执行完再删）,或者直接切 Celery。

**面试官想听的点：** 需求简单的理由,ACK 机制的缺失,改进方案(BRPOPLPUSH/Celery)

**常见踩坑：**

- 说"Celery 太重"——要解释"重"在哪里（配置复杂度 vs 实际需求）。
- 没意识到缺少 ACK——这是可靠性关键缺陷。

### Q29. PDF 上传解析的性能瓶颈在哪？

**参考答案：** `documents.py:29-47` 的 `parse_pdf_document()` 目前是同步的,在 API 请求线程中执行。对于单个 100 页以内的财报 PDF,PyMuPDF 的解析通常在 1-3 秒内完成——不是瓶颈。但如果用户上传了 5 份 500 页的年报,解析时间可能到 10-15 秒,且此时 API 线程被阻塞。

瓶颈不在于 PyMuPDF 本身的解析速度（它是 C 扩展,很快）,而在于: ① 全文文本提取后的正则匹配——`_extract_metric_hints()` 对三个指标各做多次正则搜索,在几十万字符的文本中可能慢；② 解析在请求线程中同步执行——阻塞了 API 的响应。

改进: 把 PDF 解析异步化（`asyncio.to_thread()` 或放入后台线程池）,解析完成后异步触发分析。另一个优化: 不需要提取全文——财报分析通常只需要开头几页（管理层讨论）和财务报表部分,可以用 page 索引选择性解析。

**面试官想听的点：** 1-3秒不是瓶颈,大量PDF时的阻塞问题,异步化改进

**常见踩坑：**

- 说"PyMuPDF 很慢"——它是市面上最快的 PDF 库之一。
- 没意识到 I/O 阻塞 API 线程是主要问题。

### Q31. Docker 部署有什么要注意的？

**参考答案：** `Dockerfile` 只有 16 行 (`Dockerfile:1-16`),基于 `python:3.12-slim`。需要注意的是:

1. **数据库持久化**: SQLite 文件在容器内部,容器删除后数据丢失。需要用 volume mount `-v ./data:/app/data` 来持久化
2. **Redis 依赖**: `CMD` 默认启动 API,但 worker 是单独的命令 `python start_worker.py`。生产部署需要至少两个容器——API 容器 + Worker 容器——共享同一个 Redis 和数据库 volume
3. **环境变量**: API 密钥通过 `-e DEEPSEEK_API_KEY=xxx` 传入,不要写在 Dockerfile 里。`.dockerignore` 已经排除了 `.env` 文件,防止本地密钥被打包进镜像
4. **静态文件**: Dockerfile 没有 COPY 静态文件目录——需要在构建时确保 `static/` 目录存在,否则 FastAPI 的 `StaticFiles` mount 会挂

**面试官想听的点：** volume持久化,多容器部署,环境变量安全管理

**常见踩坑：**

- 没注意 SQLite 需要 volume 持久化。
- 没提静态文件目录的潜在问题。

## 六、系统设计（5题）

### Q32. 如果数据源从 2 个公司扩展到 2000 个公司,架构需要怎么改？

**参考答案：** 当前架构的核心瓶颈在于串行处理——Retrieval 对每家公司依次调 MarketDataClient + LLM Profile 生成 + KnowledgeStore 写入。2000 家公司串行处理的延迟不可接受。

改动分三层:

1. **数据获取层**: 把 `retrieve_company_payload()` 的逐个处理改为批量——yfinance 支持一次请求查询多个 ticker（用逗号分隔）,LLM Profile 生成可以 batch prompt（一次调用处理多家公司,总 token 不超限）。这个改动可以将在 Retrieval 阶段把 N 次 API 调用减少到 O(1) 次。
2. **计算层**: Quant 的指标计算已经是纯 CPU 操作（AST 求值器无 I/O）,2000 家公司的计算可以用 `multiprocessing` 并行。
3. **存储层**: NetworkX 内存图存不下 2000 家公司的知识图谱（估计 20 万+ 节点）→ 必须切 Neo4j 或至少换 NetworkX + 磁盘持久化。

报告层需要根本性的重新设计——不能为 2000 家公司各写一份 SWOT 和投资论点。应该改为: 筛选层（Top 10 基于某种评分）+ 汇总指标（2000 家的中位数、分位数）+ 深度分析仅对 Top N。

**面试官想听的点：** 串行→批量,NetworkX→Neo4j,报告层重构,筛选+汇总+深度的分层

**常见踩坑：**

- 说"加机器就行"——架构瓶颈不在硬件,在处理模式。
- 没意识到报告层也需要重构。

### Q33. 如果要支持流式输出（SSE）,架构怎么改？

**参考答案：** 当前: 整个流水线跑完 → 返回完整结果。改为 SSE: 每个 Agent 节点完成后推送一个事件。

具体方案: FastAPI 原生支持 `StreamingResponse`。在 `graph.py:108-131` 的 `run()` 方法中,不直接 `graph.invoke()`,而是改用 `graph.stream()`——LangGraph 的 `stream()` 方法在每个节点执行后 yield 状态更新。把 yield 的每个 chunk 转为 SSE 格式 (`data: {json}\n\n`) 通过 `StreamingResponse` 返回。

前端收到的事件流示例:

```Plain
event: supervisor_done
data: {"companies": ["Apple", "Microsoft"], "plan": [...]}

event: retrieval_done
data: {"retrieved_docs_count": 2, "has_market_data": true}

event: quant_done
data: {"metrics_count": 10}
...
```

注意事项: ① SSE 是单向的(服务端→客户端),如果用户想中途取消,需要额外的 cancel API；② LangGraph 的 `astream_events` 比 `stream()` 提供更细粒度的事件（包括 LLM 调用的开始/结束）,如果需要展示"正在调用 LLM..."的 loading 状态。

**面试官想听的点：** `graph.stream()` 替代 `graph.invoke()`,SSE 格式,事件粒度设计

**常见踩坑：**

- 说"用 WebSocket"——SSE 对于单向推送就够了,WebSocket 是过度设计。
- 不知道 LangGraph 的 `stream()` API。

### Q34. 如何评估多 Agent 系统的分析质量？

**参考答案：** 这是多 Agent 系统最难的评估问题——没有 ground truth。我的思路分三层:

**第一层——结构完整性**: 报告是否包含所有预期的章节？11 个章节是否都有内容？这个可以自动化检查——`validate_report()` (`tools.py:264-270`) 检查了风险免责声明和数据来源标注。

**第二层——数据一致性**: 报告中的数字是否与原始数据一致？可以用规则验证——例如如果 `ebitda_margin = 0.34`,那么 SWOT 的 Strengths 中应该提到"强利润率"而非"利润率较弱"。这个"语义-数据对齐"可以用另一个 LLM 来检查（LLM-as-Judge）。

**第三层——分析质量**: 结论是否有洞察力？建议是否可操作？这只能人工评估——让有经验的金融分析师阅读报告并打分。如果要做大规模评估,可以用"分析报告→模拟持仓→3个月后回溯"的方式,用实际市场表现作为延迟标签,但这受市场噪音影响很大。

当前项目只实现了第一层。诚实地说,完整的三层评估需要大量的人工标注和领域专家参与,这超出了个人项目的范围。

**面试官想听的点：** 三层评估架构,LLM-as-Judge,模拟持仓评估,坦承局限

**常见踩坑：**

- 说"用准确率评估"——这没有 ground truth。
- 说"人工评估就够了"——没有提到自动化评估的尝试。

### Q35. 如果让你给这个系统加一个"记忆"功能——能记住之前的分析并在下次分析中引用——你会怎么设计？

**参考答案：** 当前系统每次分析都是 stateless 的（除了 InMemorySaver 的会话内持久化）。加跨会话记忆需要三个组件:

1. **记忆存储**: 利用已有的 KnowledgeStore（Neo4j 模式）持久化每次分析的关键结论。每次 Synthesizer 完成后,将 SWOT/投资论点/关键指标抽取为结构化摘要,写入 Neo4j 节点并与公司节点关联。例如 "2026-05-14 Analysis" → HAS_CONCLUSION → "Apple EBITDA Margin 34%, 供应链风险 medium"。
2. **记忆检索**: 每次新分析开始时,Retrieval 阶段增加一个"历史记忆检索"步骤——查询 Neo4j 中该公司的历史分析摘要（最近 N 次）,将其注入到 `document_contexts` 类似的上下文字段中。
3. **记忆引用**: 在 Synthesizer 的报告模板中增加"与前次分析的对比"章节——LLM 对比当前分析和上次分析的指标变化、风险变化、管理层语气变化,形成趋势分析。

技术挑战: 记忆的衰退和权重——3 个月前的分析结论的参考价值低于上周的。可以在检索时加时间衰减权重,或只保留最近 K 次分析。

**面试官想听的点：** 存储/检索/引用三组件,Neo4j 复用,记忆衰退,趋势分析

**常见踩坑：**

- 说"用向量数据库存历史报告"——对结构化财务数据来说,知识图谱比向量检索更合适。
- 没说记忆衰退——所有旧数据等同对待是个设计缺陷。

### Q36. 你觉得 LangGraph 这个框架有什么设计缺陷？

**参考答案：** 最大的不便: StateGraph 的编译时检查和运行时行为有差距。TypedDict 只提供类型提示,不提供运行时校验——如果一个 Agent 拼错了返回字段名,框架不会报错,只是静默地往 state 里加了一个新 key,而下游 Agent 的 `state.get("正确key")` 返回 None。这种 bug 在 7 个节点 30 个字段的系统中有时需要回溯 state JSON 才能发现。

另一个不满: conditional_edges 的路由结果必须匹配预定义的映射值——如果 `route_after_retrieval()` 返回了一个没有在映射字典中声明的值,框架的行为是......我不确定,文档里没说清楚。我投入了额外的测试来保证路由函数不会返回未声明的值。

如果能改进: 希望 StateGraph 支持 Pydantic 模型的运行时校验,至少给出 warning 而非静默;conditional_edges 的映射值应该是可选的（未匹配的走 default）,而不是强制列举。

**面试官想听的点：** TypedDict 无运行时校验,conditional_edges 映射的局限,有实际使用体验

**常见踩坑：**

- 说"没有缺陷"——任何框架都有设计取舍,不会没有缺陷。
- 说"文档不好"——这不是框架缺陷,是文档问题。

## 七、补充题（5题）

### Q37. 这个项目和传统的 FinBERT 情绪分析有什么区别？

**参考答案：** FinBERT 是一个在金融文本上微调过的 BERT 模型,做的是句子级别的情绪三分类（positive/negative/neutral）。它的优势是专用性强,劣势是只能做情绪分类,不能理解管理层发言中的战略意图、隐晦的风险提示、以及"optimistic but cautious"这种混合语气。

我的 Psychologist Agent 做的是一个双引擎设计: 规则引擎（`analyze_sentiment()`——词袋模型做正/负面词计数）提供可解释的基线;LLM 引擎（`analyze_sentiment_deep()`——DeepSeek 做整体语气、信心评分、关键主题、风险标记的四维深度分析）提供语义理解。

如果比较: FinBERT 在二分类/三分类任务上有更高的准确率（因为有微调数据）;我的系统能输出更多维度的分析（主题、风险、战略重点）,但准确率未经基准测试验证。两者不是替代关系——可以组合使用: FinBERT 做快速初筛,LLM 做深度分析。

**面试官想听的点：** FinBERT 的能力和局限,对比而非贬低,可以组合使用

**常见踩坑：**

- 说"FinBERT 过时了"——BERT 变体在特定分类任务上仍然很有用。
- 没比较两者的输出维度差异。

### Q38. 为什么 Synthesizer 用 Markdown 而不是 JSON 输出报告？

**参考答案：** 有两个原因。第一，目标读者是人——分析师、投资经理、合规审查员——他们需要可读的格式。Markdown 可以直接在 GitHub/GitLab/Notion 中渲染,也可以转换为 PDF/HTML。JSON 对机器友好但对人不友好。第二，实际的金融研究报告就是文档格式（PDF/Word）——用 Markdown 是最接近"真实交付物"的格式。

但 Synthesizer 同时也输出 JSON——在 `build_chart_data()` (`tools.py:331-399`) 中生成了结构化的图表数据（metrics_comparison/risk_radar/sentiment_distribution/agent_timeline）,这些数据专门为前端 Chart.js 可视化设计。所以可以说是: 报告正文用 Markdown（给人看）,图表数据用 JSON（给机器渲染）。

**面试官想听的点：** 读者是人,接近真实交付物,Markdown+JSON 双格式

**常见踩坑：**

- 说"Markdown 比 JSON 好"——不同用途,不是优劣问题。

### Q39. 系统中有哪些硬编码的值应该做成配置？

**参考答案：** 已经做成环境变量配置的: LLM 参数、数据库连接、Redis 连接、Neo4j 连接、行情数据源、API 端口和主机。

应该做成配置但还没有的:

- **重试阈值** `retries >= 2` (`agents.py:393`) —— 应该做成 `MAS_MAX_RETRIES` 环境变量,默认 2
- **风险评分的映射参数** —— `9.0 - margin × 15` 中的 9.0 和 15,`len(risk_flags) × 0.6` 中的 0.6,应该做成可配置的风险模型参数

### Q40. 如果让你用 LLM-as-Judge 来自动评估报告质量,你会怎么做？

**参考答案：** 用 GPT-4 或 Claude 作为评估模型（用更强的模型评估较弱的模型的输出是常见做法）。评估 prompt 设计成四个维度,每个维度 1-5 分:

1. **事实准确性**: 报告中的数字是否与输入的 `financial_metrics` 一致？（给评估模型同时输入原始数据和报告,要求逐项核对）
2. **逻辑连贯性**: 从数据到结论的推理链是否合理？（SWOT 的 Strengths 是否有对应的指标支撑？）
3. **完整性**: 11 个章节是否都有实质性内容（不是只有标题或一行占位符）？
4. **专业表达**: 语言是否达到机构研究报告标准（无口语化表达、无过度自信但不给依据的判断）？

评估模型的输出: 四维度分数 + 每个维度的具体 issue 列表。这些 issue 可以用来改进 prompt 和报告模板。

成本: 用 GPT-4 评估一份完整报告约消耗 2000-3000 tokens input + 500 tokens output,成本约 $0.03-0.05/次。用 Claude 可能更便宜但中文金融术语的理解可能稍差。

**面试官想听的点：** 四维评估,给原始数据+报告做对比,具体成本估算

**常见踩坑：**

- 说"用评分"——没说什么维度、什么标准。
- 没说评估成本——LLM-as-Judge 也需要调 API,不是免费的。

### Q41. 为什么不让用户直接和 LLM 对话来分析财报？

**参考答案：** 因为单次 LLM 对话无法提供结构化、多维度的分析。一个投研分析需要: 获取实时行情数据（LLM 不知道今天的股价）→ 解析上传的 PDF（LLM 不能读文件）→ 计算公式（LLM 做数学不可靠）→ 多维度交叉验证（单次对话容易产生确认偏误）→ 输出标准格式报告（对话式输出结构松散）。

多 Agent 系统的价值在于: 每个 Agent 强制执行一个分析步骤,步骤之间有显式的数据传递和校验。比如 Quant 必须拿到 Retrieval 的数据才能计算——如果数据不够,Replanner 会触发,而不是像对话中 LLM 可能"编一个合理的数据"来糊弄你。

换句话说: ChatGPT + 财报分析 = 一个有知识的聊天机器人; 多 Agent 系统 + 财报分析 = 一个遵循 SOP 的分析流水线。后者输出的是可审计的报告,不是一次性的对话。

**面试官想听的点：** 实时数据+PDF+数学+交叉验证+格式——不是 LLM 能力的问题,而是流程管控的问题

**常见踩坑：**

- 说"LLM 不够准确"——这过于简化了,问题是缺乏流程管控而非模型能力。

## 八、大模型算法深度（7题）

### Q42. Transformer 的 Attention 机制在你的项目中体现在哪里？

**参考答案：** Attention 不是我的代码实现的——它是 DeepSeek 模型内部的计算。但在系统设计中,我利用了 Attention 的两个特性:

1. **长上下文理解**: Synthesizer 的 prompt 包含公司画像、财务指标、情绪分析、风险评分等多个来源的信息拼接（`agents.py:424-449`）——Attention 机制让 LLM 能够在这些不同来源的信息之间建立关联,比如"注意到 Apple 的 EBITDA Margin 高 + 情绪 bullish + 供应链风险 medium → 生成'盈利能力强劲但需关注供应链集中度'的判断"。
2. **System Prompt 的角色锚定**: 我通过不同的 System Prompt 让同一个 DeepSeek 模型在不同的 Agent 中扮演不同角色（研究总监/分析师/审计师）——这依赖 Attention 对 System Prompt 的优先关注（大多数 LLM 对 System Prompt 的注意力权重高于 User Prompt）。

如果面试官追问 Attention 的数学——Q·K^T / √d_k 的 scaling factor 防止大维度导致 softmax 梯度消失。项目中 LLM 调用的 `max_tokens=220-600` 意味着每次调用的上下文窗口远小于模型的最大能力（DeepSeek 支持 64K tokens）,不需要做窗口裁剪优化。

**面试官想听的点：** 不实现 Attention 但利用了它的特性,长上下文关联,角色锚定的注意力机制

**常见踩坑：**

- 说"我的代码实现了 Attention"——没有,你用的是 API。
- 完全不提 Attention——面试官就是想看你能不能把理论和实践联系起来。

### Q43. 所有 LLM 调用都是无状态的,为什么不用 KV Cache 来加速？

**参考答案：** KV Cache 是推理引擎层面的优化——在自回归生成过程中缓存已计算的 Key 和 Value 矩阵,避免在每个新 token 生成时重新计算所有历史 token 的 Attention。这对于多轮对话特别有效——第二轮对话的 System Prompt 和第一轮相同,可以直接复用 K/V。

但在我的系统中,每次 LLM 调用都是独立的——不同的 Agent 有不同的 System Prompt,不同的 User Prompt。没有"第一轮和第二轮共用一个上下文"的场景。KV Cache 在这个架构下没有复用机会。

即使要让 KV Cache 发挥作用——比如 Retrieval 阶段的多家公司 Profile 生成共享同一个 System Prompt——这也需要 DeepSeek API 支持 prefix caching。据我所知,DeepSeek API 目前没有公开的 prefix caching 功能。如果换成 Claude API（支持 prompt caching）,可以在 System Prompt 前加 `cache_control` 标记,让相同的 System Prompt 在后续调用中被缓存。

**面试官想听的点：** KV Cache 的原理,为什么本项目用不上,什么场景适用,API 层面的限制

**常见踩坑：**

- 说"不需要 KV Cache"——不是不需要,是用不上,要解释为什么用不上。
- 混淆了 KV Cache（推理优化）和缓存 API 响应（应用层缓存）。

### Q44. 温度参数（temperature）在你的系统中为什么不超过 0.2？

**参考答案：** Temperature 控制的是 token 采样的随机性——数学上,logits 除以 temperature 后再做 softmax。T<1（如 0.2）让概率分布变尖锐——高概率 token 的概率更高,低概率 token 的概率更低,输出更确定性。T>1 让分布变平坦——增加低概率 token 被选中的机会,输出更多样但也更容易偏离事实。

金融分析需要确定性而非创意性。"Apple 的 EBITDA Margin 是 34%" 是一个事实陈述,不需要 diversity——无论生成多少次,这个句子应该是一样的。如果 temperature=0.7,LLM 可能把 34% 写成 "约三分之一"、"超过30%"、"在34%左右"——这些都是正确的表述,但在财务报告中,34% 就是 34%。

我没有在任何 Agent 中用 T>0.2,因为所有任务都是分析型而非创意型。即使用于生成企业画像（"写一段约 150 字的公司简介"）,temperature=0.2 也足够产生自然的语言表达——150 字的中文简介不需要文学创意。

**面试官想听的点：** temperature 的数学原理（logits/T → softmax）,为什么分析型任务要低温度,34% → 不能改写成"超过30%"

**常见踩坑：**

- 说"低温度更准确"——这是一个常见但不严谨的说法。低温度是确定性更高,不是"更准确"（如果模型本身就错了,低温度只会更稳定地错）。

### Q45. 你觉得 RAG 和长上下文模型（如 Gemini 2M context）在未来哪个更有前景？

**参考答案：** 两者会共存,适用不同场景。长上下文模型的优势在于简单——直接把所有文档塞进 prompt,不需要切 chunk、做 embedding、做检索。劣势在于: ① 成本——每百万 token 的推理成本是线性的,100 万 token 的 prompt 一次调用就要 $1-10；② 注意力稀释——有研究表明,模型对长上下文中部的信息关注度下降（"lost in the middle"现象）。

RAG 的优势在于: ① 经济——只把检索到的相关 chunk 放入 prompt,控制上下文长度；② 可更新——文档库更新后重新索引即可,不需要重新训练或微调；③ 可追溯——检索到的 chunk 可以显示给用户作为"参考来源"。

在当前项目中,我实际上是两种策略的混合: PDF 全文 + 样本数据 + 行情数据 + LLM 公开知识——但不是全部塞给 LLM,而是在 Retrieval 阶段做了提取和总结（`summarize_document_context()` 只保留前 1200 字符的 excerpt,而不是全文）。这是一种"结构化 RAG"——提取层提炼关键信息,而非直接向量检索。

**面试官想听的点：** 两者的优势对比,成本+注意力稀释,RAG可追溯性,本项目是混合策略

**常见踩坑：**

- 选一边站——"XX 将取代 YY"这种极端判断在面试中容易被认为是缺乏工程经验的表现。

### Q46. 为什么很多 Agent 项目用 CoT（Chain-of-Thought）,你的项目没有？

**参考答案：** CoT 适合需要多步推理的单次调用——例如"如果 A 的利润率高于 B,且 B 的研发投入高于 A,那么谁的增长前景更好？请一步步推理"。CoT 让 LLM 在输出最终答案前显式地写出推理步骤,能显著提高复杂推理任务的准确率。

我的项目选择了不同的架构来实现多步推理——把推理步骤拆到了不同的 Agent 中: 不是让一个 LLM 调用内部做 CoT,而是让 7 个 Agent 各司其职。这样做的好处是: 每个步骤的输入和输出是显式的结构化数据（JSON）,而非一段推理文本——Quant 的输出是 `{"ebitda_margin": 0.34}`,不是"Apple 的 EBITDA Margin 是 34%,这意味着..."。结构化数据让下游 Agent 可以直接使用,不需要从文本中重新提取。

但有一个地方我会考虑加 CoT: Synthesizer 的 Executive Summary 生成——目前的 prompt 要求 LLM 直接输出 4-5 句摘要,如果用 CoT（先列关键发现→再组织成摘要）,摘要的质量和结构稳定性可能会更好。

**面试官想听的点：** CoT 适用场景,本项目的替代方案（Agent 分解代替 CoT）,Synthesizer 是 CoT 的候选场景

**常见踩坑：**

- 说"CoT 没用"——不是没用,是自己的架构用不同的方式解决了多步推理。
- 说"每个 Agent 里都有 CoT"——没有,不要编。

### Q47. 你认为 AI Agent 的 Hallucination 在你的系统中最大的风险是什么？

**参考答案：** 最大风险不在 LLM 生成的分析文本（那是可读可审的）,而是在 **公司识别和数据映射阶段**。具体场景: 用户 query 是"分析比亚迪的研发投入",`extract_companies_from_query()` 的第一步是检查样本数据中没有比亚迪,第二步检查已知别名——"比亚迪"在 `COMPANY_HINTS` 中映射到 "BYD"(`documents.py:19`),股票代码映射为 "1211.HK"(`market_data.py:17`)。但如果 LLM 参与识别（第四步回退）,它可能把"比亚迪"映射到错误的股票代码（如比亚迪电子而非比亚迪股份）,导致后续所有市场数据和财务指标都基于错误代码。

这个风险比"SWOT 分析写得不够好"严重得多——因为基础数据错误会在后续的每个 Agent 中传播,而 Synthesizer 的 LLM 无法区分"yfinance 返回的数据是另一家公司的"。

目前的缓解措施: ① 公司识别优先走确定性规则（样本数据→别名→PDF 检测）,LLM 只作为最后回退;② 在 Retrieval 的 `fetch_company_snapshot()` 中返回公司全名和行业信息,为后续提供交叉验证线索;③ 报告的 Data Sources 章节声明了数据来源和方法,让读者知晓局限。

**面试官想听的点：** 不是文本层面的幻觉,而是数据映射错误,传播放大效应,缓解措施

**常见踩坑：**

- 说"报告内容可能是编的"——太泛,要说具体哪个环节最危险。
- 没说缓解措施——只指出问题不给方案是不完整的。

### Q48. 多 Agent 系统和 Model Swarm（模型群体）有什么区别？

**参考答案：** 多 Agent 系统（本项目）: 同一个 LLM（DeepSeek）,通过不同的 System Prompt 和输入数据扮演不同角色。Agent 之间有显式的流水线和数据传递,控制流由代码定义。

Model Swarm: 多个不同 LLM（或同一 LLM 的不同实例）并行生成多个候选回答,然后通过投票/评分/辩论选出最佳回答。典型例子是 Chatbot Arena 的"多个模型各生成一个回答,用户投票"。

核心区别: 多 Agent 是**分工协作**（每个 Agent 做不同的事）,Model Swarm 是**冗余竞争**（多个模型做同一件事,选最好的结果）。金融分析场景适合分工协作——一个人负责收集数据,一个人负责计算,一个人负责写报告——而不适合让七个模型各自写一份完整报告然后投票,因为报告质量没有客观标准。

模型群的优势在于需要创造力的场景（如文案生成——生成 5 个版本让用户选）,劣势在于成本高（N 倍 LLM 调用）且不适合有明确分工的任务。

**面试官想听的点：** 分工 vs 冗余,金融分析不适合群投票,成本差异

**常见踩坑：**

- 说"模型群就是多个 Agent"——混淆了分工和冗余的概念。
- 说"我的系统也是模型群"——不是。

### Q49. 你对 Agent 框架（LangChain/AutoGPT/CrewAI/Dify）的生态怎么看？

**参考答案：** 这是一个快速演化的领域,但我觉得有一个趋势: 框架正在从"让 LLM 做一切决策"向"开发者显式定义控制流"回摆。

AutoGPT 和 CrewAI 的早期版本高度依赖 LLM 做任务规划和路由——理念是"给 LLM 一个目标和工具,让它自己想办法"。这在 demo 中看起来很惊艳,但在实际应用中面临三个问题: ① LLM 的规划不可预测（同样的输入可能走不同的路径）;② 成本高（LLM 的每次"思考下一步做什么"都要调 API）;③ 容易陷入循环（LLM 反复尝试失败的工具调用）。

LangGraph 和 Dify 的工作流模式代表了"显式控制流"方向——开发者定义节点和边,LLM 在节点内执行具体任务,控制流由代码保证。这更接近传统软件工程的可测试性和可维护性。

我的项目在 LangGraph 中是偏向"显式控制流"一端的——路由不走 LLM,所有 Agent 分工由代码定义。这是金融场景的选择,不是技术教条。

**面试官想听的点：** 从 LLM 驱动回到显式控制,举具体框架的例子,可测试性

**常见踩坑：**

- 说"XXX 框架不好"——框架选择取决于场景,不是好坏。
- 只说观点不给原因——"显式控制流更好"需要解释为什么。

### Q50. 如果你有无限的算力和数据,这个项目最想加的一个 feature 是什么？

**参考答案：** 我会加一个**反向压力测试引擎**。当前的风险分析是正向的——给定指标,计算风险分数。反向压力测试是: "在什么条件下,Apple 的财务风险会从 4.5 升到 8.0？"——系统反推出需要的条件组合（如 EBITDA Margin 下降到 10% + 供应链风险升级为 high + 管理层信心降到 3/10）。

技术实现: 用优化算法（如贝叶斯优化或简单的网格搜索）在风险模型的输入空间（EBITDA Margin/供应链等级/情绪评分/市场位置）中搜索,找到使风险评分超过阈值的参数组合。然后让 Synthesizer 为每种参数组合生成对应的情景叙事——"如果发生以下情况...公司的风险将显著上升"。

这个功能的价值: 让分析从"描述现状"升级到"预判临界点"——告诉投资者什么信号值得关注,什么条件下应该减持。当前的五维风险评分是对现状的快照,反向压力测试是对可能性的探索。

为什么需要"无限算力": 当前风险模型有约 10 个自由参数,网格搜索在小空间内可行,但如果加入更细粒度的宏观经济变量（利率/汇率/GDP增速）和行业竞争变量,搜索空间会爆炸。

**面试官想听的点：** 反向压力测试的概念,技术实现思路,为什么有价值,为什么需要更多资源

**常见踩坑：**

- 说"换个更强的模型就行"——这是偷懒答案,没体现出你对系统的思考。
- 说一个和项目完全无关的 feature——要基于现有架构做延伸。
